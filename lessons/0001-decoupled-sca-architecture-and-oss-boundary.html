LESSON 0001 / PHASE 1 · 统一底座架构 / 约 18 分钟

第三代 SCA 四层解耦架构与「借力 vs 自研」边界划分

从 0 到 1 启动商业化 SCA 产品矩阵之前，总架构师必须先拍板的第一个决策：为什么不能让开源扫描器定义你的数据模型，以及如何在 Apache-2.0/MIT 合规红线下精准分配自研弹药。

本课收获：独立画出四层解耦蓝图并完成 MVP 模块的「借力/自研」边界评审 速查卡片：四层契约与开源协议速查表
为什么先学这一课（对齐你的 Mission）

你的目标是在 1–3 个月内拍板全场景统一底座，并且未来要在同一底座上平滑长出第三代壁垒（可达性、恶意包、AI-BOM）。几乎所有 0→1 的 SCA 团队栽的第一个大跟头，都不是算法不够难，而是第一天就把“扫描工具”当成了“平台架构”。

010→1 的头号架构陷阱：为什么 80% 的团队会在第 6 个月推倒重写？

当你从零搭建 SCA，最诱人的捷径是：“先封装一个成熟的开源全能扫描器（比如直接调用 Trivy CLI），把输出的漏洞 JSON 落库、套一层前端管理台，两周就能出 Demo。”

这正是第一代 / 第二代 SCA 的「扫描器中心（Scanner-Centric）」心智：把 资产提取 → 漏洞匹配 → 告警展示 耦合成一条黑盒流水线。它在第 1 个月跑得飞快，但会在第 6 个月遭遇三次毁灭性撞墙：

三代 SCA 的本质代差 第一代：靠文件名/哈希/CPE 做扁平组件清单与 NVD 匹配；
第二代：解析包管理器依赖树 + 切入 CI/CD 与 IDE 自动化提 PR；
第三代 + AI 时代：以统一图模型为中心，叠加函数/运行时可达性降噪、恶意包行为分析与 AI-BOM（模型/数据集/MCP 依赖）治理。
  1. 数据模型被上游 CLI 绑架：当你想同时整合 Syft（容器镜像强）+ cdxgen（复杂源码构建强）+ 自研 Java/C++ 解析器时，不同工具输出的字段、依赖边语义与证据格式互不兼容，你的数据库表结构被迫打满补丁。
  2. 无法“一次采集、持续重算”：明天突然爆出一个新的高危 0-day（类似 Log4Shell 或新的 npm 投毒链）。如果你的核心表存的是“上次扫描出的漏洞列表”，而不是“独立且完整的依赖图谱（SBOM IR）”，你就必须重新拉起全公司几千个仓库和镜像重扫一遍。
  3. 第三代高价值能力无处挂载：静态可达性分析需要把函数调用路径挂接到图上的某个(组件 PURL, 精确版本, 符号坐标)节点；VEX 需要记录“为何此路径不可达”；AI-BOM 需要把模型权重文件与训练数据集作为一等公民接入同一依赖图。扁平的扫描结果表根本撑不住这些关系。

总架构师第一条铁律：开源扫描器是可插拔的“传感探头”，绝不能成为你平台的“脊椎”。平台的脊椎必须是你 100% 自主掌控的统一中间表示（Unified IR）。

02第三代 SCA 的四层解耦架构

要同时满足“全场景覆盖（源码/构建/镜像/制品/AI）”、“高效借力开源底座”与“聚焦高价值差异化壁垒”，现代 SCA 平台必须严格按数据流与变更频率切分为四层。每一层有清晰的输入输出契约，并对应截然不同的「借力 vs 自研」策略：

印证视角：全球商业标杆是如何在这四层下注的？

拆解全球最成功的三家新一代商业标杆，你会发现一个惊人的共识：没有一家把核心研发浪费在“从零重造所有 OS/锁文件提取器”上，它们全部在 Layer 2 标准契约稳固后，各自在 Layer 3 或 Layer 4 打穿一个极深护城河：

架构参考原型 开源平台 OWASP Dependency-Track（Apache-2.0）就是典型的「L1 与 L2–L4 解耦」参考架构：它自己根本不做源码扫描，而是专注于摄入标准 CycloneDX SBOM，并在服务端持续重算漏洞与 VEX 状态。
  • Snyk（重仓 Layer 3 情报研判 + Layer 4 开发者修复流）：不仅聚合 NVD/生态公告，还持续监控 GitHub 提交与 PR 并在 CVE 正式分配前由人工团队研判出 SNYK-* 条目，叠加严谨版本区间与自动修复 PR 图谱。
  • Endor Labs（重仓 Layer 1 构建保真度 + Layer 4 函数级可达性）：直击传统 SCA 告警泛滥的死穴，通过静态分析跨直接与传递依赖构建深层函数调用图（Call Graph），验证应用入口是否真的会调用漏洞函数，将噪音压降 90% 以上。
  • Socket.dev（重仓 Layer 3 实时注册表监控 + Layer 4 行为分析）：跳出“等 CVE 出来再告警”的滞后模式，在包发布和安装边界对代码做 AST 静态行为检测（70+ 红旗信号：网络外联、读取 .env/SSH 密钥、postinstall 脚本、代码混淆、维护者突变），主动拦截 0-day 投毒包与 AI Agent Skills 恶意投毒。

03站在巨人肩膀上：开源底座选型与商业协议排雷

在你的商业闭源交付红线下，选型开源底座必须同时过两关：① 协议合规关（不仅是主代码许可证，还要查清配套规则库与数据集的衍生许可）；② 工程集成深度关（库级嵌入 vs CLI 进程封装）。

开源底座 / 工具 实测许可证 商业闭源判定 核心工程价值与架构定位
Google OSV-SCALIBR Apache-2.0 首选 · 库级嵌入 Google 内部大规模使用的 Go 模块化 SCA 引擎，驱动 OSV-Scanner v2。天然按 Extractor / Enricher / Detector 插件分层，可直接作为 Go 库引入并按需替换或追加自研插件。
Anchore Syft Apache-2.0 首选 · 库级嵌入 容器镜像分层、OS 包数据库（dpkg/rpm/apk）与制品元数据编目（Cataloging）的行业标杆；同样是 Go 库与 CLI 双形态，和 Grype 构成经典的提取/匹配解耦范式。
OWASP cdxgen Apache-2.0 推荐 · 隔离封装 多语言构建感知（Build-aware）覆盖面极广，原生输出 CycloneDX 1.6/1.7（支持 CBOM 与 AI/ML-BOM）。因依赖 Node.js 与各语言构建环境，最适合封装为独立沙箱 Worker。
OSS Review Toolkit (ORT) Apache-2.0 推荐 · 参考/封装 调用原生包管理器精确还原复杂源码传递依赖树，是高保真依赖解析与企业级许可证合规的绝佳工程蓝本（Kotlin/JVM）。
Aqua Trivy Apache-2.0 合规 · 谨防锁死 极佳的全能扫描参考与离线数据库分发范例（BoltDB/OCI），但若把它直接当作核心数据底座，极易陷入第 01 节的“扫描器中心”重构债。
ScanCode-Toolkit 代码 Apache-2.0
数据 CC-BY-4.0		 可用 · 注意数据署名 源码许可证识别标杆。代码本身可商用，但配套的 ScanCode LicenseDB 采用 CC-BY-4.0，商业分发时必须履行清晰的署名与修改说明义务。
Semgrep CE 引擎 LGPL-2.1
官规 Semgrep Rules v1.0		 边界高敏 · 规避官规 核心引擎为弱传染 LGPL-2.1（需严格隔离链接边界）；更隐蔽的坑在于Semgrep 官方维护规则集明确限制用于竞品商业 SaaS，不可拿其规则打包售卖。
FOSSology / CodeQL GPL-2.0 / GitHub 专有条款 严禁闭源产品嵌入 FOSSology 主体为强传染 GPL-2.0；CodeQL 默认免费条款仅限开源代码或学术研究，商业私有代码扫描必须购买 GHAS，两者均不可作为商业 SCA 产品底座。

关键工程权衡：库级嵌入 (Library) vs 进程封装 (CLI Adapter)

同样是 Apache-2.0 底座，集成方式不同，工程掌控力天差地别：

隐性成本提醒 无论选择 Library 还是 CLI，在进入 Layer 2 前都必须强制经过一层反腐败适配器（Anti-Corruption Adapter），把外部结构体翻译成你自己的内部 IR（含 PURL + 证据链 + 依赖边）。

库级嵌入（如 Go 引入 OSV-SCALIBR / Syft）

推荐用于核心扫描引擎

优势：零子进程开销、内存内流式转换、可精细裁剪插件（关掉不准的 Extractor，注入自研 Extractor）、统一错误遥测与超时控制。

代价：绑定宿主语言生态（Go），需建立上游版本升级的回归测试防线。

隔离进程封装（如沙箱运行 cdxgen / ORT）

推荐用于异构构建环境

优势：天然跨语言隔离（Node.js / JVM / 原生包管理器）、防止构建期扫描污染宿主环境或触发恶意构建脚本安全风险。

代价：序列化与容器启动开销较高，需做并发队列与只读挂载/断网沙箱控制。
