01四大 Apache-2.0 提取底座：源码级架构与核心接口

商业闭源 SCA 最忌讳把开源工具当黑盒命令行去包一层壳——一旦遇到断网私有化、多模块并发、或单生态解析翻车，黑盒会让你无从插桩也无从替换。下面直接看四大引擎的源码级接口与管道抽象：

商用协议核验结果 本课拆解的 4 大底座——OSV-SCALIBR、Anchore Syft、OWASP cdxgen 与 ORT——主仓库均为 Apache-2.0，满足商业闭源嵌入或适配封装前提（仍需常规保留版权声明与 NOTICE）。

1. Google OSV-SCALIBR

Go 库优先 · 驱动 OSV-Scanner v2
Apache-2.0 
// FilesystemExtractor (extractor/filesystem): 零打开预过滤 + 提取
FileRequired(api filesystem.FileAPI) bool
Extract(ctx context.Context, input *filesystem.ScanInput) (inventory.Inventory, error)

// Enricher (enricher): 联网/图谱补全 (如 transitivedependency/pomxml)
Enrich(ctx context.Context, input *enricher.ScanInput, inv *inventory.Inventory) error

// Capabilities (plugin): 按离线/OS/权限动态裁剪插件
plugin.FilterByCapabilities(plugins, &plugin.Capabilities{
  OS: plugin.OSLinux, Network: plugin.NetworkOffline,
})
  • 核心管道：FilesystemExtractor + StandaloneExtractor 产出统一 Inventory，再由 Enricher（如结合 deps.dev 算无锁 pom.xml）与 Detector 接力增强（见 插件矩阵 与 Enricher 文档）。
  • 杀手锏：天生为进程内 Go 库嵌入设计；FileRequired 避免无谓文件读取，FilterByCapabilities 让政企断网私有化一键摘除在线 Enricher 而不超时。
  • 硬伤与边界：对复杂 DSL 构建（Gradle Groovy/Kotlin、setup.py）及企业级许可证深度合规管线非其强项。

2. Anchore Syft

Go 库 & CLI · 容器/制品提取标杆
Apache-2.0 
// 核心 Go 管道 (github.com/anchore/syft/syft)
src, _ := syft.GetSource(ctx, "registry:app:1.0", syft.DefaultGetSourceConfig())
// DefaultCreateSBOMConfig() 可配 source.SquashedScope(终态) vs AllLayersScope(全层)
bom, _ := syft.CreateSBOM(ctx, src, syft.DefaultCreateSBOMConfig())

// *sbom.SBOM 核心图对象
bom.Artifacts.Packages   // *pkg.Collection (pkg.Cataloger 产出)
bom.Relationships        // []artifact.Relationship (DependencyOf/Contains)
  • 核心管道：把任意镜像/Tar/目录抽象为 source.Source，并行调度按生态分组的 pkg.Cataloger，输出强类型的 *sbom.SBOM（见 Go Pkg Docs）。
  • 杀手锏：OCI 镜像分层（SquashedScope vs AllLayersScope）、OS 包库（dpkg/rpm/apk）与二进制制品（Fat-JAR / Go BuildInfo）提取业界顶级；且与 Grype 天然验证了「提取与匹配解耦」。
  • 硬伤与边界：默认走静态纯数据路径；扫未带锁源码或需要执行包管理器的深度传递图时（例如无锁 Java/Go 传递边），覆盖深度有明显天花板。

3. OWASP cdxgen

Node.js CLI / Server · 全能 CycloneDX 1.7 引擎
Apache-2.0 
// 安全模式 vs 构建感知模式 (lib/cli/index.js → createBom)
// 注：pre-build 默认隐含 --no-install-deps，可再配 CDXGEN_SECURE_MODE=true
cdxgen --lifecycle pre-build --no-install-deps -o bom.json
cdxgen --lifecycle build --deep --spec-version 1.7

// 输出原生 CycloneDX 1.7 高阶结构
// - properties: internal:workspaceRef (Monorepo 子包关联)
// - evidence.identity[].methods[{technique, confidence}]
// - 顶层 citations[] (pointers/expressions) / modelCard / cryptoProperties
  • 杀手锏：生态覆盖极广，原生围绕 CycloneDX 1.7 设计，对 JS/Python Monorepo（internal:workspaceRef）、CBOM、ML-BOM 及 evinse（AST 证据流）支持最领先。
  • 高危安全红线：cdxgen 默认走 build 生命周期并调用 mvn / gradle / npm 等原生构建工具，扫不可信仓库存在两类典型风险：构建文件任意代码执行（CVE-2024-50611）与旧版 Maven 模块路径命令注入（GHSA-5vwr-qchf-q4pf，需升级 12.3.3+）。静态快速扫必须强加 --lifecycle pre-build --no-install-deps（或开启 CDXGEN_SECURE_MODE=true），跑 build 模式必须丢进 Lesson 0003 隔离沙箱！

4. OSS Review Toolkit (ORT)

Kotlin JVM · 高保真有效图与合规管线
Apache-2.0 
// Analyzer 核心模型 (oss-review-toolkit.org)
PackageManager (Maven / GradleInspector / Pip / Npm)
  → 精准归类 Scope (compile / runtimeClasspath / testCompileClasspath)
  → 全局去重有向图 DependencyGraph (避免子项目重复树爆炸)
  → OrtResult (analyzer-result.yml → Downloader/Advisor/Evaluator)

// 工程哲学：默认 allowDynamicVersions = false 拒猜动态范围！
  • 杀手锏：不偷懒、不瞎猜，面向企业法务与高保真审计（见 Analyzer 文档）。DependencyGraph 跨多模块去重极省内存，按 Scope 彻底切分生产运行态与测试构建态，为许可证合规与无误报有效图提供黄金标准。
  • 硬伤与边界：JVM 启动与内存较重，依赖原生包管理器工具链（JDK/Gradle/Python 等）协同；绝对不适合同步高频快速扫，最佳落位是「客户 CI Hook 或异步隔离深度通道」。
底座引擎 形态与嵌入方式 最擅长的战场 工程盲区与安全雷区 断网私有化表现 商业平台推荐定位

02双泳道编排路由与反腐败适配层（Orchestrator + ACL）

既然 4 个引擎各有神通也各有暗伤，总架构师的正确姿势绝不是“全仓全量把 4 个 CLI 串行跑一遍”，而是设计一个能力感知路由器（Capability-Aware Router）分流到两条执行泳道，并在出口处架设一道铜墙铁壁般的反腐败适配层（Anti-Corruption Layer, ACL）。

架构主权红线 如果让 *sbom.SBOM（Syft）或 OrtResult（ORT）直接穿透到平台数据库和漏洞匹配层，只需半年你的代码库就会彻底“长死”在第三方工具的结构上。ACL 必须把一切外部格式无状态地翻译成自研结构体。

03多提取器置信度融合与消歧算法

当两个提取器对同一个项目给出不一致的结果时，绿地团队最容易踩进两个相反的极端：要么取简单并集（Naive Union）——把静态猜测的错误版本和真实构建版本全塞进库里，瞬间引爆 Ghost CVE 误报；要么取简单交集（Naive Intersection）——因为 OS 包工具不认识 Python 锁文件、或版本号不一致，交集直接变空集，制造大规模漏报灾难。

工业级架构必须基于「解析阶梯置信度模型」与「四条融合铁律」做确定性裁决（并对齐 CycloneDX 1.7 的 evidence.identity 与顶层 citations 规范）：

证据阶梯（Tier） 默认置信度 典型产出提取器与方法 CycloneDX evidence.identity 技术映射与裁决权
Tier 4 · 交付产物 0.96 – 0.98 Syft (SquashedScope OS DB / Fat-JAR pom.properties / Go BuildInfo) technique: binary-analysis / manifest-analysis；代表最终交付态绝对真值，可覆写源码静态猜测。
Tier 3 · 构建有效图 0.95 – 0.96 ORT (CI Hook / GradleInspector) / 隔离沙箱 cdxgen --lifecycle build technique: manifest-analysis (build-time)；含完整 Scope 边与调解结果，接管无锁动态项目。
Tier 1 · 确定性锁文件 0.90 – 0.93 OSV-SCALIBR (uv.lock/pnpm-lock.yaml/Cargo.lock) / cdxgen pre-build technique: manifest-analysis；在执行 PEP 508 Markers 求值后具有极高确定性，与同阶梯引擎可证据叠加。
Tier 2 · 虚拟求解 0.80 – 0.85 OSV-SCALIBR (transitivedependency/pomxml via deps.dev / 私服只读 API) technique: manifest-analysis (registry-resolved)；在无源码构建前提下推演 Effective POM，劣于 Tier 3/4，优于 Tier 0。

铁律 1 · 单版本生态：冲突必覆写（Supersede）

Java (Maven/Gradle)、Python (同一环境)、Go (同一主版本) 在同一构建单元内只能生效唯一版本。按 (project_root, base_purl) 分组后，高置信度 Tier 直接覆写低阶版本；被淘汰的版本记入 citations[] 标注 superseded_lower_tier，绝不写为有效节点。

铁律 2 · 多版本生态：按路径分治（Path-Scoped）

npm / pnpm / yarn 允许同一包多版本合法嵌套共存。融合分组键必须扩展为 (canonical_purl, install_subpath)：不同路径的 lodash@4.17.21 与 @4.17.15 各自保留独立 bom-ref；只有路径也一致时才做证据合并。

铁律 3 · 异构资产域：互补并集（Disjoint Union）

Syft 提取的 OS deb/rpm 包、OSV-SCALIBR 提取的应用 pypi/cargo 包、cdxgen 提取的 huggingface 模型属于互不重叠的资产域，必须执行并集以补全盲区；同时对容器历史删除层（Whiteout）做隔离，不污染运行态清单。

铁律 4 · 图边与证据：最细粒度富化叠加

当两个高阶引擎在同一个组件节点上达成一致时（例如 OSV-SCALIBR 提取节点，ORT 或 cdxgen 补充了 runtime/test 边或 internal:workspaceRef），保留最精细的 Scope 与有向边，合并去重 occurrences[]，并在顶层 citations[] 并列署名。
