1 人 + AI 模块化单体架构：Go↔Python 强契约与快慢双路径任务编排

很多技术负责人一旦立项企业级平台，就会本能地画一张包含 10 个微服务的拓扑图——在 15 人团队里这叫组织拆分，但在 「1 人架构师 + AI Coding Agents」 模式下，早产微服务等于把 AI 的上下文窗口撕成十块碎片，还会让私有化客户面对十几个镜像望而却步。本课拍板 Go 模块化单体 + Python 专项 Worker + ConnectRPC 强契约 + 三段式队列演进，让一个人就能跑出十人团队的稳定交付力。

本课收获：划定 Go 与 Python 的物理进程边界；用 ConnectRPC + Buf（Apache-2.0）锁死跨语言契约防 AI 漂移；掌握 PG SKIP LOCKED / River（MPL-2.0）→ NATS JetStream → Kafka 演进阶梯与快慢双路径防雪崩状态机 前置关联：Lesson 0006 (多触点) · Lesson 0018 (Python AI 安全) · Lesson 0023 (产品域模型)
为什么「模块化单体 + 隔离 Worker」是 AI 协同研发的最优解？

AI Coding Agent 最怕跨 8 个独立微服务仓库的隐式 JSON 契约变更——改了上游忘了下游、本地起不来集成测试。把全部控制面逻辑（鉴权、域台账、L1/L3 核心、策略、调度器）收敛在一个编译为单一二进制的 Go Modular Monolith 内（内部严格按 Go `internal/` 包划清模块接口），仅在「语言生态刚需（Python AI/模型解析）」与「安全隔离刚需（不可信构建期沙箱）」两处切出独立进程，既守住高内聚，又为未来水平扩缩容留好无痛切口。

01三层物理拓扑：Go 单体核、Python 专项 Worker 与构建沙箱

1.1 严守「双语言职责单向分工」，绝不让 Python 抢控制面

在 Go + Python 双栈团队里，最容易出现的架构腐化是“随手在 Python 里又写一套 HTTP API、又连数据库改 Finding 表”，最后演变成双大脑架构。基于前 22 课沉淀的 SCA 技术栈，我们把全系统运行态收敛为 3 个边界极度清晰的物理单元：

Go 与 Python 为什么不是“对称双写”？ 我们的主存储引擎、OSV-SCALIBR/Syft 采集核、Sigstore 验签、cel-go 网关和 CLI/MCP/Hook（Single Go Core）全部是 Go 生态；Python 的不可替代价值只在 AI 模型格式生态（HuggingFace / Safetensors / PyTorch AST / 学术静态分析）。让 Go 充当唯一系统大脑，Python 保持无状态专职计算节点，运维心智直接减半。
运行单元与主力语言 内部模块划分（强边界） 资源特征与扩缩容方式 架构禁忌（Red Lines）
1. Go Control Plane & Core Scanner
（Go 模块化单体 · 可按 Role 启动）		 internal/auth · internal/domain · internal/orchestrator · internal/l1_l3 · internal/policy CPU/内存均衡；同一二进制通过 --role=api|worker|all 启停：单机私有化跑 all，SaaS 独立扩展 worker。 严禁模块间绕过 Service Interface 直接 JOIN 对方私有表；禁止在控制面进程内直接跑不可信用户构建脚本。
2. Python AI & Deep Analysis Worker
（Python ASGI / Worker 进程）		 AI-BOM 模型/数据集血缘提取、深度学习 AST/序列化特征、特定 Python 静态调用图分析。 大内存/多进程（asyncio + ProcessPool 防 GIL 阻塞）；按专职队列独立扩缩容。 严禁直接写入核心业务表！只能通过强类型响应回传结构化 IR/Evidence，由 Go 控制面校验入库。
3. Untrusted Build Sandbox
（gVisor / Kata / Firecracker）		 运行 cdxgen --lifecycle build、Maven/Gradle/npm 原生解析等可能触发恶意 postinstall 的重任务。 一次性短命隔离容器/MicroVM（无内网凭据、白名单出口代理、严格 CPU/内存/Timeout 限制）。 严禁和主业务数据库在同一网络平面内运行；容器销毁即彻底清理磁盘缓存。

02Go ↔ Python 强类型契约：用 Protobuf + ConnectRPC 锁死 AI 协同边界

2.1 为什么不要用“手写 Flask JSON 字典”做跨语言通信？

当 1 个人指挥 AI Agent 同时修改 Go 调用方和 Python 处理端时，最常见的隐蔽 Bug 是：AI 在 Python 端把字段 package_purl 顺手改成了 purl，或者把毫秒时间戳传成了秒，静态类型检查完全抓不到，直到线上半夜扫到特定样本才静默崩溃。

解决方案是把所有 Go ↔ Python 边界收敛到唯一一份 proto3 契约目录下，配合 Buf CLI（Apache-2.0）与 ConnectRPC（connect-go 与 connect-py，均为 Apache-2.0）：

  • 一处定义、双端代码生成：每次 AI 修改接口，CI 强制校验 buf breaking 与 buf generate，Go 结构体与 Python dataclass/protobuf stub 编译期对齐。
  • 原生兼容 HTTP/JSON + gRPC + Streaming：connect-py（支持 ASGI uvicorn 与 asyncio）无需像传统 gRPC 那样强依赖复杂 Envoy 代理；既能用二进制 Protobuf 跑内网高速 RPC，调试时还能直接用 curl -H "Content-Type: application/json" 复现现场！
  • 大文件零拷贝传递指针，不传 4GB 模型体：RPC 请求体永远只传对象存储/本地共享卷的 artifact_uri、sha256、max_bytes_budget 与 traceparent（W3C 链路追踪上下文），绝对禁止把几十 MB 的 SBOM 或几 GB 的模型权重塞进 RPC Payload。
Go 模块化单体为何支持 `--role=all|api|worker`？ 这是双模兼容的神器：在客户内网单台 8C16G 机器上，运维只需起 1 个 Go 二进制（--role=all）+ 1 个 Python Worker + 1 个 PG，5 分钟拉起整套平台；到了 SaaS 万级负载时，同一份镜像用 Helm 分别部署 --role=api 和 --role=worker 即可水平扩缩。

03零重型运维队列演进阶梯 & 快慢双路径防雪崩状态机

3.1 三段式异步队列演进（拒绝 Day-1 引入重型集群）

很多人在第一天就把 Kafka + ZooKeeper/KRaft + Temporal 全家桶搬进私有化安装包，结果安装脚本 800 行、调试一次消费积压半天过去了。我们把 ScanQueue 抽象成极简的 Go Interface（Enqueue / Claim / Ack / Nack），按客户规模与产品阶段分三步平滑演进：

演进阶段与选型 精确开源协议 核心工程机制与优势 适用上限与商用合规边界
Stage 1 · Day-1 极简态
PG SKIP LOCKED / River		 PostgreSQL License / MPL-2.0 (River) 直接复用主库 PostgreSQL，与创建 Snapshot/ScanJob 共用同一个 ACID 事务入队，100% 消除“写库成功但发 MQ 失败”的双写丢单，私有化零额外中间件。 轻松承载 ~500–2,000 任务/秒；注意 River 为 MPL-2.0（文件级弱传染）：作为未修改 Go 依赖库直接 import 完全合法闭源，若修改 River 自身源文件则改动文件须开源。
Stage 2 · 成长/高并发
NATS JetStream		 Apache-2.0 Go 原生单二进制（<30MB），内建持久化 Stream、WorkQueue 语义、Ack 等待与消费者组；既可独立运行也适合嵌入企业私有化集群。 承载数万级消息/秒，把高频扫描心跳与重算流从 PostgreSQL 连接池彻底剥离，保住数据库稳定。
Stage 3 · 超大型/长周期
Apache Kafka + Temporal		 Apache-2.0 / MIT Kafka 支撑十万+事件扇出（参考 Lesson 0006 Hyades v5）；Temporal 管理跨数小时的沙箱构建 + 静态/动态多阶段可恢复编排。 仅面向超大规模 SaaS 或大型集团部署启用，不捆绑进中小私有化默认安装包。

3.2 致命陷阱防范：快慢双路径隔离、幂等键与租户公平调度

哪怕队列再快，如果把“凌晨 5,000 个项目的 0-day 全网重算”和“开发者等在面前的 15 秒 PR 门禁 / 1.5 秒 Agent MCP”放进同一条 FIFO 队列，早高峰 PR 必然全部超时红灯。必须从第一天建立三条编排铁律：

  1. 快慢双路径（Fast Lane vs Slow Lane）硬隔离：lane=interactive（Agent MCP / PR Diff）拥有独立 Worker 池或高优先级抢占槽位，SLA 硬卡 P95 < 15s；lane=batch（全量镜像、0-day 重算、C/C++ 同源）独立池运行，绝不互相饿死。
  2. 幂等键去重（Idempotency Key）：队列消息与入库统一绑定幂等键 (tenant_id, asset_id, commit_sha_or_digest, scan_profile)；处于 PENDING/RUNNING 状态的重复 Webhook 请求直接合并等待同一结果，省去 CI 抖动带来的数十倍冗余计算。
  3. 租户令牌桶 + 有界状态机 + 死信隔离（DLQ）：单租户突增提交时由带配额的公平调度防止挤占全站资源；每条 ScanJob 显式经历 PENDING → RUNNING(Lease 心跳) → SUCCEEDED / RETRY_BACKOFF → DEAD_LETTER，遇到畸形文件或 OOM 毒丸任务超过 3 次自动隔离进 DLQ 并告警，杜绝无限重入拖死整群 Worker。
Lease 心跳租约防“僵尸任务” Worker 抢到任务后必须每隔 10 秒续期 lease_expires_at。若某个 Pod 因 OOM 被 K8s Kill，30 秒后租约过期，调度器自动安全回收并重投（且每次重投递增 attempt_count），绝不依赖不可靠的内存态信号。
