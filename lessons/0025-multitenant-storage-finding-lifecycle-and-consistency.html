多租户隔离（PG RLS）、Finding 稳定指纹状态机与 Outbox 多存储一致性

安全产品一旦发生“B 公司在界面里看见了 A 公司的漏洞或私有组件名”，商业信誉当天归零；而“昨天刚豁免的误报，今天改个目录名字就重新弹窗”，则会让研发彻底卸载你的工具。在 Lesson 0021 拍板的 CAS + Hot(PG) / Warm(ClickHouse) / Cold(S3) 存储底座之上，本课聚焦工程落地最隐蔽的三大硬伤：SaaS 与私有化共用的 PostgreSQL RLS 四重隔离防线、Finding 跨重构指纹与 5 态生命周期机、以及保证 PG ↔ ClickHouse / RoaringBitmap 绝不脑裂的 Transactional Outbox。

本课收获：掌握一套 Schema 兼容 SaaS 多租户与私有化单租户的 PG 16+ RLS + sqlc（MIT）防漏写法；设计稳定 Finding 指纹与状态转移；用 Outbox + ReplacingMergeTree（Apache-2.0）消除多存储脑裂 前置关联：Lesson 0021 (CAS 与三层存储) · Lesson 0023 (域模型) · Lesson 0024 (Go↔Python 边界)
为什么「1 人 + AI Agent」特别依赖数据库引擎级 RLS 兜底？

当 AI Coding Agent 帮你在几十个 Go Handler 里飞速编写复杂 JOIN 查询时，人工 Review 很容易看漏某条子查询少写了一个 AND tenant_id = $1。如果仅仅靠应用层“自觉加 WHERE”，迟早会发生跨租户泄密。把隔离规则下沉到 PostgreSQL 引擎内部的 Row-Level Security（RLS），再用 Go 的 WithTenantTx 事务包裹器在入口统一锁定上下文，等于给 AI 生成的所有 SQL 套上了一道无法绕过的内核保险丝。

01一套 PG Schema 兼容 SaaS 与私有化：RLS 四重保险丝

1.1 为什么选「共享表 `tenant_id` + PG RLS」，而非“每租户一个独立 Schema/库”？

很多架构师在启动期纠结：SaaS 要不要给每个租户建一个独立 PostgreSQL Schema 或独立数据库？对于只有 1 个架构师 + AI 的团队，千万不要轻易采用“千租户千 Schema”——一旦你有 800 个租户，一次表结构升级（Migration）就要轮询执行 800 遍 DDL，连接池碎片化也会瞬间把 PG 内存吃干。

正确的双模统一设计是：所有业务表全量携带 tenant_id UUID NOT NULL（建议按 (tenant_id, ...) 做复合主键/索引前缀），借助 PostgreSQL 原生 RLS 实现硬隔离——公有云 SaaS 传入各自租户 UUID，私有化单租户只需传入固定默认 DEFAULT_TENANT_ID，Migration 脚本、sqlc 生成代码与测试套件 100% 复用！但要让 PG RLS 真正不翻车，必须同时锁死以下 4 条生产红线：

大客户物理隔离合规诉求怎么接？ 若有头部金融客户购买 SaaS 专属独享实例（Single-Tenant VPC），直接用这完全相同的容器镜像配一个专属 PostgreSQL 实例运行即可——tenant_id 退化为单常量值，代码一行不改。
RLS 防线检查项 常见致命踩坑（Silent Failure） 正确生产配置标准 双模 & AI 协同收益
1. 连接池事务绑定
SET LOCAL vs SET		 用 PgBouncer 事务连接池时写会话级 SET app.current_tenant，事务结束后变量仍残留在连接上，直接污染下一个租户！ 必须包装在显式 BEGIN ... COMMIT 内执行 SET LOCAL app.current_tenant = '...'，事务一结束自动销毁变量。 Go pgx（MIT）封装唯一入口 WithTenantTx(ctx, tid, fn)，彻底禁止裸拿池连接。
2. 强制覆盖表 Owner
FORCE ROW LEVEL SECURITY		 PG 默认表创建者（Table Owner）自动绕过 RLS；很多团队拿同一个 DB 账号既跑 Migration 又跑后端服务，导致 RLS 零生效。 全表声明 ALTER TABLE ... FORCE ROW LEVEL SECURITY，同时将运维迁移账号与后端运行池账号拆开。 CI 自动化巡检 pg_class.relforcerowsecurity = true，一键防退化。
3. 禁用跳过权限
NOBYPASSRLS		 应用服务账号误授予 SUPERUSER 或 BYPASSRLS 属性，一切 RLS 规则直接失效。 应用池角色严格创建为 NOSUPERUSER NOCREATEDB NOBYPASSRLS，仅后台跨租户异步调度使用受审计的受限视图。 就算 AI 写出漏掉 tenant_id 的 SQL，数据库也会按策略拦住跨租户行。
4. 失效默认关闭
Fail-Closed 策略表达式		 漏设上下文时报错崩溃或落入错误默认租户；或者写 current_setting(..., false) 引发热路径高频异常日志。 策略统一采用 tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid，未设置时求值 NULL 零行返回。 配合 sqlc（MIT）生成只接受 TenantTx 接口的 DAO 方法，双层防线闭环。

02Finding 跨重构稳定指纹与 5 态生命周期机

2.1 怎样设计指纹，才能抗住目录重命名与版本小补丁升级？

承接 Lesson 0023 的 LogicalFinding 设计，决定用户体验成败的核心在于指纹（Fingerprint）怎么算。如果指纹里直接哈希了当前文件绝对路径 /services/old-pay/pom.xml 和瞬时版本 2.14.0，只要研发把目录改名为 /services/checkout/pom.xml 或把漏洞包从 2.14.0 升到仍受影响的 2.14.1，原有 VEX NOT_AFFECTED 豁免立刻断链！

经过工业界验证的稳定指纹公式遵循「业务资产锚定 + 忽略易变物理路径 + 去版本组件坐标」原则：

finding_fingerprint = SHA256(
  tenant_id | asset_id | logical_branch |
  canonical_purl_without_version |   // 如 pkg:maven/org.apache.logging.log4j/log4j-core
  canonical_vuln_or_rule_id |        // CVE / OSV Alias 主键 / 恶意包 MAL-* / License Rule
  reachable_symbol_or_empty          // 可达性函数符号（如开启函数级粒度）
)

而当前所在路径（manifest_path）与具体命中的包版本（detected_version）仅作为随每次 Snapshot 刷新的可更新属性字段挂在 LogicalFinding 行上，绝不参与主键指纹哈希。

什么时候该拆成多条 Finding？ 同一个应用里若不同模块同时引入了两个不兼容大版本（如 npm 合法多版本共存 lodash@3.x 与 lodash@4.x）且对应不同调用路径或不同主版本，可在指纹中保留 major_slot 或 subproject_key，防止误合并。

2.2 5 态生命周期与 Python Worker 写入隔离契约

LogicalFinding 必须严守单向/受控状态转移，不允许扫描器随意覆盖人工决策：每次新 Snapshot 入库时，仅对 OPEN 和 FIXED 执行自动状态跃迁（若原本 FIXED 但新快照又检出则置为 REOPENED 并递增 reopen_count）；若人工已标记 VEX_NOT_AFFECTED 或未过期的 SUPPRESSED，扫描器绝不能将其重置回 OPEN，仅更新 last_seen_snapshot_id。

同样地，针对 Lesson 0024 中的 Python 专项 Worker：由于 Python 侧只承担无状态解析（AI-BOM / 序列化扫描 / 学术图谱计算），Python 进程连业务数据库账号权限都不需要拥有，所有结果经 ConnectRPC 返回给 Go 控制面的 WithTenantTx 事务统一完成 Fingerprint 归并、状态转移和 Outbox 落盘。

03Transactional Outbox 保障 PG ↔ ClickHouse / RoaringBitmap 一致性

3.1 彻底根除「写 PG 成功、同步 ClickHouse / 内存索引失败」的双写脑裂

在 Lesson 0021 中，我们用 PostgreSQL 承载热资产与交易状态，用 ClickHouse（Apache-2.0）跑 Warm 层趋势统计大盘，用内存 RoaringBitmap（Apache-2.0）做 10 秒 0-day 位图检索。如果 AppSec 在页面上把 200 条漏洞批量标为 VEX_NOT_AFFECTED，后端直接写 PG 后再异步 HTTP 写 ClickHouse，一旦中间进程重启或网络闪断，CISO 的大盘数字和 AppSec 工作台就会永久对不上。

工业界最省心、对 1 人 + AI 团队零额外分布式事务成本的方案是 Transactional Outbox + ClickHouse 幂等去重引擎：

  1. PG 同事务写 Outbox 表：在 Go 的 WithTenantTx 事务里修改 logical_findings 的同时，往同一张 PG 库的 outbox_events 表插入一行事件（含全局递增序列号或事务版本号 version、tenant_id 与序列化 Payload）。
  2. 轻量 Poller 或 Debezium CDC 投递：Day-1 直接在 Go 单体里起一个轻量异步轮询协程批量消费 outbox_events（单机/中小 SaaS 零新增运维组件）；超大规模时再无缝替换为 Debezium（Apache-2.0）读取 PG WAL 写入 Kafka。
  3. 下游幂等收敛（At-Least-Once 安全消费）：Outbox 保证“至少投递一次（可能重复）”。内存 RoaringBitmap 更新天然幂等（重复置位不影响集合）；ClickHouse 宽表采用 ReplacingMergeTree(version, is_deleted)（Apache-2.0），以 (tenant_id, finding_id) 为 ORDER BY 排序键，后台 Merge 自动淘汰旧 version 行，实时大盘查询配合 FINAL 或 argMax 即可拿到 100% 精确一致的当前风险水位。
私有化单机需要强制装 ClickHouse 吗？ 不需要！极简私有化模式下，CISO 趋势视图的 Outbox 消费者可以直接降级写入 PG 分区汇总表或内嵌分析引擎——只要写操作统一经过 outbox_events 事件总线，双模底层存储就能自由插拔。
