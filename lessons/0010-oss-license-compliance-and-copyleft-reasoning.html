01三层真值模型与 SPDX 表达式语法树（AST）

1.1 Declared vs Observed vs Concluded：为什么不能只信清单字符串？

第一代扫描器常见一个致命天真假设：直接从 package.json、pom.xml 或 Cargo.toml 读出 license 字段就敢给出“合规/高危”结论。现实工程里，上游包元数据经常出现三类失真：① 写非标文本（如 "See LICENSE" 或 "BSD" 导致机器报 NOASSERTION）；② 夹带源码未报（清单宣称 MIT，但源码深处抄入一个 GPL-2.0-only C 文件）；③ 漏掉归属附件（只标 Apache-2.0 却未收集包内 META-INF/NOTICE.txt）。

因此，我们的 Layer 2 IR 与对外交换规范（CycloneDX 1.7 acknowledgement 字段与 SPDX 3.0.1 SimpleLicensing / ExpandedLicensing）必须严格切分三层许可证真值：

  • Declared（声明态）：组件作者在包管理器清单或根 LICENSE 中主动声明的许可。CycloneDX 1.7 中以 acknowledgement: "declared" 表达，只能作“快速初筛证据”，不可直接当作最终法律定性。
  • Observed / Discovered（实测证据态）：由源码/制品文件扫描器（如 google/licensecheck 或 ScanCode-Toolkit）逐文件探测到的许可证头、版权行与 NOTICE 原文，写入 evidence.licenses 与 citations。
  • Concluded（裁定真值态）：综合 Declared、Observed、社区校对库（如 ClearlyDefined）及法务手工修订（Curation）后收敛出的唯一有效 SPDX 表达式（acknowledgement: "concluded"），供下游策略引擎与 Notice 生成器消费。
CycloneDX 1.7 Schema 写法防踩坑 在 CycloneDX 1.7 JSON 中，expression 是 licenses[] 元素的直接字段，不能嵌套在 license 子对象里面！即单个 ID 写为 {"license": {"id": "Apache-2.0", "acknowledgement": "declared"}}，而复合表达式必须写为 {"expression": "MIT OR Apache-2.0", "acknowledgement": "concluded"}。

1.2 SPDX v3.0.1 Annex B 运算符优先级：为什么“子串匹配”必死？

假设一个核心依赖声明了 LGPL-2.1-only OR BSD-3-Clause AND MIT。如果用朴素的“正则切词 / 包含 LGPL 即报警”方案，或者按从左到右结合去猜语义，结果全错！按照 SPDX 规范 v3.0.1 Annex B 的正式 ABNF 文法，表达式必须严格遵循四级运算符绑定优先级（从最紧到最松）：

  1. +（or-later 后缀，最高优先级）：紧贴单个许可证 ID 右侧（如历史写法 GPL-2.0+，SPDX 3.0 推荐归一化为 GPL-2.0-or-later）。
  2. WITH（例外修饰符，仅次于 +）：只能原子绑定单个许可证与一个合法 Exception ID（如 GPL-2.0-only WITH Classpath-exception-2.0），绝不允许跨括号修饰复合表达式。
  3. AND（合取，高于 OR）：同时约束。上例右侧 BSD-3-Clause AND MIT 先结合为一体！
  4. OR（析取，最低优先级）：多选一双/多许可。上例完整 AST 实际等价于 LGPL-2.1-only OR (BSD-3-Clause AND MIT)——商业闭源产品只需在策略节点自动选定右支 BSD-3-Clause AND MIT，即可完全合法放行！
SPDX 语法大小写与自定义引用 SPDX v3.0.1 Annex B 规定布尔运算符须全大写（AND / OR / WITH）或全小写（and / or / with），严禁大小写混写（如 And / Or），工程上推荐统一输出全大写以兼容 SPDX 2.x 解析器；许可证/例外 ID 本身大小写不敏感，但自定义前缀 LicenseRef-<id>、AdditionRef-<id> 与跨文档前缀 DocumentRef-<doc>:LicenseRef-<id> 必须严格区分大小写，引擎遇到 LicenseRef-* 时默认路由至法务规则映射表或人工复核。
Go 核心 AST 合规求值骨架：OR 择优剪枝 vs AND 义务合并与双向冲突校验 纯 Go 嵌入式引擎（可复用 github/go-spdx 解析 AST），零子串误报 
type EvalContext struct {
    Distribution string // "SAAS_ONLY" | "ON_PREM_BINARY" | "OSS_APACHE2" | "OSS_GPL2"
    Linking      string // "STATIC" | "DYNAMIC" | "IPC_PROCESS" | "MODIFIED_SRC"
    Scope        string // "RUNTIME" | "DEV_TEST" (源自 Lesson 0002 IR Edge Scope)
}

func EvalLicenseAST(node ExprNode, ctx EvalContext) PolicyVerdict {
    switch n := node.(type) {
    case *OrNode:
        // OR 节点：分别求值左右子树，自动选举风险与传染代价更低的分支，剪枝另一支！
        left := EvalLicenseAST(n.Left, ctx)
        right := EvalLicenseAST(n.Right, ctx)
        return pickLowerRiskBranch(left, right)

    case *AndNode:
        // AND 节点：合并两侧全部履约义务，并执行 OSADL/FSF 双向互斥冲突检查
        left := EvalLicenseAST(n.Left, ctx)
        right := EvalLicenseAST(n.Right, ctx)
        merged := mergeVerdicts(left, right)
        if conflict := checkPairwiseIncompatible(left.Leaves, right.Leaves, ctx); conflict != "" {
            merged.Decision = DecisionBlock
            merged.Reasons = append(merged.Reasons, conflict)
        }
        return merged

    case *WithNode:
        // WITH 例外（如 GPL-2.0-only WITH Classpath-exception-2.0）仅在未改动原库自身时免除链接传染
        return evalLeafWithException(n.LicenseID, n.ExceptionID, ctx)

    default:
        return evalLeafWithException(n.(*LeafNode).LicenseID, "", ctx)
    }
}

02三维上下文传染性推理矩阵与协议双向兼容性（OSADL / FSF）

2.1 传染性不是“许可证的静态标签”，而是三维上下文函数

同样一个 GPL-3.0-only 或 LGPL-3.0-only 组件，在不同架构部署与依赖位置下，法律后果天差地别。现代化合规引擎绝不能按许可证单表一刀切，必须基于「分发形态（Distribution）× 链接/修改方式（Linking）× 依赖作用域（Scope）」三维矩阵做上下文求值：

Go / Rust / Webpack 隐形暗坑：静态链接 LGPL 许多研发团队记住“LGPL 属于弱传染，商业闭源可用”就盲目放行了，却忽略了 LGPLv2.1 §6 与 LGPLv3 §4(d) 的核心前提——允许用户自主替换修改后的 LGPL 库！C/Java 动态加载 .so / .jar 没问题，但 Go 单文件二进制、Rust 静态编译或前端 Webpack 单包打平 时用户无法替换该库，此时若不改用动态链接或向客户交付闭源主程序的可重链接目标文件（Object Files），同样构成严重违约！

2.2 不可忽视的「协议间双向互斥（AND Compatibility）」检查

许多工程团队甚至商业产品只检查“单个许可证会不会传染我的闭源主程序”，却漏掉了 同一款产品或开源组件内部依赖之间在 AND 组合时的互相冲突（License Incompatibility）——这是 FSF 官方兼容性准则 与 OSADL 开源许可证兼容性矩阵 重点解决的难题：

组合对 / 方向（Inbound + Outbound） 兼容性裁决 底层法律与条款根因（FSF / OSADL） 工程引擎解决与放行策略
Apache-2.0 + GPL-2.0-only 双向互斥（BLOCK） Apache-2.0 的专利终止与赔偿条款构成了 GPLv2 §6 所禁止的“额外限制（Further Restriction）”。 检查目标是否写为 GPL-2.0-or-later（可升级至 GPLv3）；否则必须剔除或替换其中一方。
Apache-2.0 → GPL-3.0-only 单向兼容
整体变为 GPL-3.0		 GPLv3 §7 显式允许加入与 Apache-2.0 一致的专利报复及归属补充条款；但反过来 GPL-3.0 不能合入 Apache-2.0 作品。 兼容性推理图必须是有向图（Directed Graph）：compat(Inbound, Outbound) 不可随意交换方向！
GPL-2.0-only + GPL-3.0-only 双向互斥（BLOCK） GPLv2 与 GPLv3 在反 Tivoization 与专利条款上无法互认，两份都写死 -only 时无法找到交集许可。 只有当其中一方为 GPL-2.0-or-later 时，才可向上对齐收敛为 GPL-3.0。
GPL-3.0-only + AGPL-3.0-only §13 桥接升格
整体升为 AGPL-3.0		 常规条款本不互通，但 GPLv3 / AGPLv3 第 13 条专设交叉互操作豁免，允许组合且要求整套联合作品遵循 AGPL 网络源码义务。 引擎须建模“传染升格传播（Escalation）”：即使你的项目原本只标 GPL-3.0，只要链接了 AGPL-3.0，对外 SaaS 立刻触发全套 §13 披露！
