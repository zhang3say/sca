构建溯源与密码学证明：SLSA v1.2、in-toto 与 Sigstore 闭环

过去 19 课我们打造了极强的“事后成分扫描与行为检测”体系，但它依然回答不了一个终极问题：你部署进生产环境的容器镜像、npm 包或大模型权重，真的由受控源码经受控 CI/CD 构建产出，还是在仓库、构建机或制品库被半路调包？随着 SLSA v1.2（2025 年 11 月 24 日正式发布）将 Source Track（L1–L4） 纳入正式规范，结合 in-toto Statement v1 / DSSE PAE、Sigstore Bundle v0.3（Fulcio + Rekor v2 + TUF） 与 VSA 预验签摘要，我们终于能把“扫描出来的清单”升级为“密码学不可伪造的端到端信任链”。

本课收获：吃透 SLSA v1.2 Build（L1–L3）与 Source（L1–L4）双轨及连续性铁律；掌握 in-toto v1、DSSE PAE 防类型混淆、VSA（verification_summary/v1）与 Fulcio V2 OID 身份绑定；划清 PyPI PEP 740 / npm Provenance、公共 Rekor 泄密红线、Private Sigstore（Rekor v2 Tile）与全 Apache-2.0 商业栈落地边界 先修底座：Lesson 0002 · Lesson 0005 · Lesson 0017
架构师核心命题（开启 Phase 3 · 从“检测漏洞”跃迁到“证明清白”）

在 SolarWinds 与 XZ Utils 式供应链投毒中，最终落盘的二进制根本没有已知 CVE；在现代云原生与 AI 交付中，如果缺乏源码审查连续性证明 + 隔离构建 Provenance + 不可变 Digest 绑定签名，任何基于可变 Tag 的 SBOM 都会在构建后被静默调包。你的第三代 SCA 底座必须在 Layer 2 IR 上原生接纳 in-toto DSSE Attestation & SLSA VSA，把“可信溯源证明”变成与漏洞、恶意包并列的第三大核心资产证据柱。

01SLSA v1.2 双轨模型：为什么仅有 Build Track 依然会失守？

1.1 从 Build-only 到 Source + Build 双轨治理（2025-11-24 正式发布）

早期 SLSA v1.0 只聚焦构建环节（Build Track）：证明制品确实产自某台隔离的 CI Runner，且构建过程未被篡改。但工程实战很快暴露了一个致命盲区：如果拥有合并权限的内部人员或被盗维护者账号直接向 main 分支强推了一段后门代码，甚至临时关闭分支保护两小时后再恢复，隔离完美的 Build L3 流水线依然会忠实地把恶意代码编译并签发“完全合规的 Build Provenance”！

为此，SLSA v1.2（2025 年 11 月 24 日定稿）正式将 Source Track（L1–L4） 升级为与 Build Track 并列的规范轨道，并在验证摘要（VSA）中同时输出 SLSA_SOURCE_LEVEL 与 SLSA_BUILD_LEVEL，让下游消费方一眼看清“源码是否合规入库”与“构建是否未遭篡改”。

SLSA v1.2 Source Track 的“连续性铁律”（Onboarding & Continuity） SLSA v1.2 明确规定：源码安全等级仅自开启技术控制的时刻（Onboarding）起向前生效，绝不做历史追溯背书！如果某个受保护分支曾被管理员临时关闭强推保护或审查要求哪怕一小时，连续性（Continuity）即告断裂，系统必须吊销或降级其 Source 等级并要求重新建立审查基线。
轨道与等级 核心规范要求 防御的供应链威胁 SCA 平台校验与证据字段
Build L1
（存在溯源描述）		 构建流程产出机器可读的构建 Provenance（含源码输入、构建指令与制品摘要）。 人工误打包、缺失制品来源元数据、无法追溯上游 Commit。 校验存在 https://slsa.dev/provenance/v1 声明且 subject.digest 与产物一致。
Build L2
（托管构建 + 签名）		 必须由托管构建服务执行，并由服务本身对 Provenance 进行密码学签名。 构建完成后到制品库之间的中途篡改与伪造构建描述（防构建后篡改）。 验证 DSSE 签名及 Fulcio 证书来自受信任的 CI/CD OIDC 平台（非开发者本地笔记本）。
Build L3
（加固临时隔离环境）		 每次构建运行在强隔离、临时化（Ephemeral）Runner 中，构建步骤间无法偷改签名密钥或缓存。 同机并发任务跨构建投毒、构建脚本窃取签名私钥（防构建中篡改）。 核对 builder.id 属于高隔离托管 Runner URI（例如官方 GitHub Hosted / 隔离 K8s Tekton Pod）。
Source L1 & L2
（版本控制 + 防篡改历史）		 L1 要求不可变 Commit SHA 与可审计 Diff；L2 要求源码控制系统阻止强推改写历史并实时签发 Source Provenance/VSA。 未托管源码直接发包、git push --force 掩盖恶意修改痕迹。 核对源码 VCS Commit SHA 可达，且 Source Control System 启用历史不可变审计日志。
Source L3 & L4
（持续控制 + 双人审查）		 L3 要求对受保护分支/标签持续强制执行组织策略并证明连续性；L4 强制 Two-Party Review（且新推送自动作废旧审批）。 单人内部作恶（Insider Threat）、账号被盗后绕过审查直接合并恶意 PR。 校验 Source VSA 中的 SLSA_SOURCE_LEVEL_3/4 与分支保护连续性时间戳，未达标则在发版门禁拦截。

02密码学协议栈：in-toto v1、DSSE PAE、Sigstore 与 Trusted Publishers

2.1 为什么要用 DSSE PAE？告别脆弱 JSON 规范化与类型混淆

任何可信溯源证明在落盘时都由三层标准自内向外嵌套封装：

  • 最内层 · in-toto Statement v1（https://in-toto.io/Statement/v1）：把“证明对象”和“声明内容”严格绑死——包含 _type、subject（数组，每项必须携带不可变密码学 digest 如 sha256）、predicateType（如 https://slsa.dev/provenance/v1、https://slsa.dev/verification_summary/v1 或 https://cyclonedx.org/bom）与 predicate。
  • 中间层 · DSSE（Dead Simple Signing Envelope）：将 Statement 编码为 Base64 放入 payload，并标明 payloadType: "application/vnd.in-toto+json"。签名时不直接对原始 JSON 或乱序换行签字，而是对 PAE（Pre-Authentication Encoding） 字节流签名：
    PAE(type, payload) = "DSSEv1" + SP + LEN(type) + SP + type + SP + LEN(payload) + SP + payload（其中 SP 为 0x20，LEN 为精确字节长度的十进制 ASCII，无前导零）。它一举消除了易碎的 JSON Canonicalization 依赖，并彻底堵死跨协议 Type Confusion（类型混淆） 攻击。
  • 最外层 · Sigstore Bundle v0.3 & Trusted Publishers：用 OIDC 短期身份令牌向 Fulcio 换取短命 X.509 代码签名证书（内嵌不可伪造的 Provider-agnostic V2 DER UTF8String 扩展 OID：.1.8 OIDC Issuer V2、.1.9 Build Signer URI、.1.12 Source Repository URI、.1.21 Run Invocation URI），并把签名记录写入不可篡改透明度日志 Rekor（Rekor v2 引入 Tile-backed 瓦片存储，大幅削减对象存储与索引运维成本）。全部证书链与日志包含性证明（Inclusion Proof）打包进单个 .sigstore.json（Bundle v0.3），配合 TUF 分发的 Trusted Root 即可在客户现场完全离线验签。
致命误区：“通过 Sigstore 验签 ≠ 可以信任该制品” 任何人都可以在自己的公共 GitHub 仓库注册一个账号，用 GitHub OIDC 经公共 Fulcio 签出数学上 100% 合法的 Sigstore 签名！如果只调用 verify 而不强制锁定 OIDC Issuer（OID .1.8）+ 精确 Workflow SAN（OID .1.9）+ 源仓 URI（OID .1.12）+ 不可变制品 Digest，就会沦为典型的 Confused Deputy。

2.2 生态实践：PyPI PEP 740、npm Provenance 与 VSA 预验签捷径

下游包管理器的无密钥革命：PyPI 通过 PEP 740（Digital Attestations） 为每个 .whl/.tar.gz 分发文件同时承载 PyPI Publish（证明经 Trusted Publisher 认证）与 SLSA Provenance 双证明，彻底淘汰长期泄露风险极高的静态 PYPI_API_TOKEN；npm Provenance 与 GitHub Artifact Attestations 同样采用 OIDC + Sigstore 将发布包与具体源码 Commit 强绑定。

消费端性能破局 · VSA（https://slsa.dev/verification_summary/v1）：生产 K8s 准入节点或客户交付侧若每次部署都递归拉取几百层上游依赖的原始 Provenance 日志并逐条解析，不仅延迟极高，而且上游仓库策略细节往往不便对外暴露。VSA 允许受信任的中心策略引擎完成一次全量校验后，签发一张极简结论证书：包含 verifier.id、policy、verificationResult（PASSED/FAILED）以及达标列表 verifiedLevels（如 ["SLSA_BUILD_LEVEL_3", "SLSA_SOURCE_LEVEL_3"]），让边缘节点与客户侧亚毫秒级放行。

03全 Apache-2.0 商业底座选型与 Pure Go sigstore-go 验签原语

3.1 商业闭源生态矩阵：全栈 Apache-2.0 的罕见黄金赛道

与二进制同源或自动修复赛道不同，SLSA / in-toto / Sigstore 核心开源生态几乎清一色采用纯宽松的 Apache-2.0 协议。架构师真正要防范的不是传染性 GPL，而是“误把内部闭源数据写入公共透明度日志”的运维与隐私泄密红线：

开源项目 精确许可协议 核心能力定位 商业闭源集成与数据主权边界
sigstore/sigstore-go Apache-2.0 Sigstore 官方轻量级 Go SDK，专注嵌入 SCA 内核执行 Bundle v0.3 / DSSE / TUF 验签与策略校验。 核心嵌入式首选：极低依赖体积，直接作为 Layer 2/L4 验签库编译进你的 Go 后端与 CLI。
sigstore/cosign & oras-go Apache-2.0 容器镜像、SBOM 与 OCI 1.1 Referrers 签名/绑定与推送拉取标准工具链。 OCI 分发伴生层：用 oras-go 在 Go 内核原生读写 OCI Referrers，实现制品、SBOM 与 Bundle 同仓随行。
in-toto/attestation & witness Apache-2.0 官方 Statement v1 / VSA Protobuf Schema，以及可插拔 CI 构建过程证明收集器（witness）。 Schema 与收集器：直接复用官方 Go Struct 建模；跨 GitLab/Jenkins/自建 CI 可借力 witness 采集步骤级证据。
slsa-framework/slsa-verifier Apache-2.0 SLSA 官方独立校验器，对照 SLSA Build/Source 策略深度核验 Provenance 与构建器信任级别。 语义规则参考/嵌入：可复用其 Builder 信任校验逻辑，配合自研策略引擎输出 SLSA VSA。
sigstore/model-transparency Apache-2.0 Sigstore 面向 AI 模型的无密钥签名工具链（model-signing），专治 GB 级权重目录/Safetensors 完整性。 衔接 Lesson 0017–0018：将模型权重签名纳入统一 Sigstore Bundle 验签体系，防权重替换投毒。
guacsec/guac & kyverno Apache-2.0 GUAC 将 SBOM、VEX、Provenance 与 VSA 聚合成可查询图谱；Kyverno 负责 K8s 准入策略强拦截。 私有化主权铁律 全栈协议安全，但企业私有仓绝不能用公共 Rekor！必须部署私有 Fulcio + Rekor v2 + TUF Trusted Root。

3.2 Pure Go 核心原语：基于 sigstore-go 的三要素锁定与 VSA 解析

下面这段 Go 核心代码直接嵌入你的商业 SCA 平台验签引擎：通过本地/私有 TUF Trusted Root 初始化 verify.NewVerifier，严格锁定制品 sha256、预期 OIDC Issuer（.1.8）与受保护分支发布工作流 SAN，随后解码 DSSE 内嵌的 in-toto Statement v1 并校验 SLSA v1.2 VSA 双轨等级：

Go 核心原语：sigstore-go 三要素验签 + SLSA v1.2 VSA 双轨策略裁决 Zero-Keyless-Spoof Pure Go Provenance Verifier（Apache-2.0 生态） 
import (
    "encoding/hex"
    "encoding/json"
    "fmt"

    "github.com/sigstore/sigstore-go/pkg/bundle"
    "github.com/sigstore/sigstore-go/pkg/root"
    "github.com/sigstore/sigstore-go/pkg/verify"
)

type InTotoVSAStatement struct {
    Type          string `json:"_type"`
    PredicateType string `json:"predicateType"`
    Predicate     struct {
        VerificationResult string   `json:"verificationResult"`
        VerifiedLevels     []string `json:"verifiedLevels"`
    } `json:"predicate"`
}

// VerifyArtifactAndVSA 使用私有或官方 TUF TrustedRoot 锁定制品摘要、OIDC 身份与 SLSA v1.2 双轨等级
func VerifyArtifactAndVSA(
    trustedMaterial root.TrustedMaterial,
    sigBundle *bundle.Bundle,
    artifactSHA256Hex, oidcIssuer, exactWorkflowSANRegex string,
) (*verify.VerificationResult, error) {
    // 1. 强约束校验透明度日志（Rekor v2）与 SCT，缺一不可
    sev, err := verify.NewVerifier(
        trustedMaterial,
        verify.WithSignedCertificateTimestamps(1),
        verify.WithTransparencyLog(1),
    )
    if err != nil {
        return nil, fmt.Errorf("init sigstore verifier: %w", err)
    }

    digestBytes, err := hex.DecodeString(artifactSHA256Hex)
    if err != nil {
        return nil, fmt.Errorf("decode artifact sha256: %w", err)
    }

    // 2. 必须锁定 Issuer（OID .1.8）+ 精确 Workflow SAN，防任意 Fork 冒充（Confused Deputy）
    certID, err := verify.NewShortCertificateIdentity(oidcIssuer, "", "", exactWorkflowSANRegex)
    if err != nil {
        return nil, fmt.Errorf("build certificate identity: %w", err)
    }

    // 3. 执行离线/在线 Bundle v0.3 验签：同时绑定不可变制品 Digest 与证书身份
    res, err := sev.Verify(
        sigBundle,
        verify.NewPolicy(
            verify.WithArtifactDigest("sha256", digestBytes),
            verify.WithCertificateIdentity(certID),
        ),
    )
    if err != nil {
        return nil, fmt.Errorf("sigstore verification rejected: %w", err)
    }

    // 4. 解析 DSSE 内部 Statement v1，确认 SLSA v1.2 Build + Source 双轨达标
    if res.Statement != nil && res.Statement.PredicateType == "https://slsa.dev/verification_summary/v1" {
        raw, _ := json.Marshal(res.Statement)
        var vsa InTotoVSAStatement
        if err := json.Unmarshal(raw, &vsa); err == nil && vsa.Predicate.VerificationResult != "PASSED" {
            return nil, fmt.Errorf("VSA policy result not PASSED: %s", vsa.Predicate.VerificationResult)
        }
    }
    return res, nil
}
