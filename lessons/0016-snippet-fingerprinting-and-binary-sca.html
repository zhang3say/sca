开源代码片段同源检测与无源码二进制 SCA 底层原理

此前 15 课的架构依赖一个隐含前提：目标软件至少存在包管理器清单（package.json / pom.xml / go.mod）或编译内嵌元信息（.go.buildinfo / OS dpkg 库）。但在真实商业场景中，客户往往把 C/C++ 源码直接 Copy-Paste（Vendoring）、静态链接进 strip -s 剥离符号的可执行文件，或者交付一个没有任何源码的黑盒路由器固件与商用 .so/.dll。本课带你设计Zero-Source-Upload 代码同源指纹与三层二进制特征金字塔，并严防 SCANOSS（GPL-2.0）与 cve-bin-tool（GPL-3.0）商用红线。

本课收获：吃透 Type-1~4 代码克隆与 Winnowing（t = w+k-1）数学保证；落地 CENTRIS 嵌套冗余消除与最早提交溯源；掌握 Layer A/B/C 三层二进制特征金字塔（OSSPolice / B2SFinder / Gemini ACFG）；严格切分 LIEF/Binwalk v3/TLSH/Capstone/Ghidra 纯宽松商用栈与 GPL 雷区 先修底座：Lesson 0002 · Lesson 0005 · Lesson 0010
架构师核心命题（对齐你的 MISSION.md）

在我们的 MISSION.md 中，C/C++ 无源码二进制逆向与代码片段同源曾被列为统一底座稳定后的专项拓展。进入 Phase 2 后，汽车电子、IoT 固件、基础软件及金融黑盒采购审计客户往往直接卡死在这一关：“没有 package.json，只有 firmware.bin 和外包给的 libalgo.so，或者研发直接把开源函数复制进业务 C 文件里改了变量名，你们的 SCA 能不能抓出 GPL 传染和老版本 CVE？” 破解之道在于：不破坏原有 Layer 2 统一 IR，而是为 Layer 1 新增「Snippet Fingerprinter」与「Binary Feature Extractor」，输出带 confidence 置信度的 CycloneDX 1.7 组件证据。

01为什么传统清单与精确哈希对 C/C++ 和 Copy-Paste 完全失明？

1.1 无清单软件供应链的三大真实盲区

与 npm、Maven、PyPI、Go Modules 等现代生态不同，C/C++ 与嵌入式软件长期处于“碎片化构建 + 手工移植”状态。在商业客户现场，以下三类场景会让纯 Manifest/Lockfile SCA 交出白卷：

  • ① 源码片段级 Copy-Paste（Vendoring / 摘抄复用）：开发者从 GitHub 复制了一个 120 行的 CRC32 或 JSON 解析函数放进 src/utils/，顺手删掉了顶部版权头，并把变量名全改了一遍——里面可能潜藏 GPL-3.0 传染风险或早已修复的缓冲区溢出漏洞。
  • ② 静态链接 + strip -s 剥离符号：嵌入式或商用 C/C++ 程序习惯将 zlib、libpng、OpenSSL 编译成静态库 .a 合入最终 ELF 可执行文件，再执行 strip --strip-all 抹除 .symtab 与调试符号，连文件边界都被打平。
  • ③ 黑盒商用 SDK 与固件镜像：甲方从外部供应商采购闭源驱动 .so / .dll 或整包嵌入式固件（SquashFS / U-Boot / CramFS），源码根本不可见，必须在不反编译出可读明文的前提下识别其夹带的过期开源组件。
客户隐私红线：Zero-Source-Upload（源码零上传） 商业客户极度抗拒把核心闭源 C/C++ 源码明文上传到你的云端 SaaS 做同源比对。因此现代商业 SCA（参照 Black Duck Protex 与 SCANOSS .wfp 模式）必须采用「客户端本地单向提取局部哈希指纹 → 仅上传稀疏哈希集合至云端倒排索引匹配」架构：指纹不可逆推回原代码，既打消客户保密顾虑，又把网络传输压缩到百 KB 级。

1.2 四级代码克隆光谱（Type-1 ~ Type-4）与检测技术选型

学术界与工业界普遍采用 Roy & Cordy 提出的四级代码克隆模型来衡量同源检测引擎的抗修改能力。架构设计时必须明确每一级克隆应由哪种哈希或图算法承接，切忌企图用单一精确 MD5/SHA256 包打天下：

克隆级别 代码修改特征 典型工程现身场景 对应指纹算法与失效边界
Type-1（完全克隆） 除空白、缩进与注释外，代码完全相同。 直接复制整个文件或未改写的代码块（Vendoring）。 去除空白/注释后的 Winnowing 字符级指纹即可近 100% 召回。
Type-2（重命名克隆） 结构一致，但修改了变量名、函数名、类型名或常量字面量。 外包或研发“洗白式”抄袭开源工具函数，全局替换标识符。 Token 归一化（折叠标识符为 ID）+ Winnowing；纯字符/字节级哈希在此处 0 命中！
Type-3（增删改克隆） 在函数内增删、重排了若干语句（通常改动 10%–30%）。 从开源库摘出模块后，裁剪多余分支并补充业务错误处理逻辑。 函数级分段 + TLSH 局部敏感哈希或 AST 子树特征；整文件哈希全面失效。
Type-4（语义克隆） 语法与结构完全不同，仅实现等价计算逻辑（如递归改迭代）。 手写重新实现或经过编译器高度内联优化后的二进制跨架构函数。 源码层极难低误报检索；二进制层依赖 控制流图嵌入（ACFG / Gemini） 召回。

02源码片段同源检测：Winnowing、TLSH 与 CENTRIS 嵌套溯源

2.1 Winnowing 算法：用 $t = w + k - 1$ 数学下界击穿片段漏报

如果把全网开源仓所有文件的每个 k-gram 哈希都存进索引，索引体积会膨胀几十倍。Saul Schleimer、Daniel Wilkerson 与 Alexander Aiken 在 ACM SIGMOD 2003 经典论文 Winnowing: Local Algorithms for Document Fingerprinting（驱动了著名查重系统 MOSS）中给出了优雅的局部指纹挑选定理：

  1. 词法预处理与 k-gram 切片：先剔除注释和多余空白（若抗 Type-2 则利用 Tree-sitter（MIT）将标识符统一折叠为占位符 ID），再以滑动步长 1 切分长度为 k 的序列并计算滚动哈希（如 CRC32C / FNV-1a）。
  2. 窗口最右最小值挑选：设保证检测下界为 t 个字符/Token，定义滑动窗口大小 w = t - k + 1。窗口依次滑过哈希序列，在每个窗口中仅记录最小哈希值（若并列最小，必选最靠右的那一个），且相同位置不重复入库。

核心数学保障：只要两段代码共享任何长度 $\ge t = w + k - 1$ 的连续片段，该算法在数学上100% 保证两者至少选中一个相同的指纹哈希；同时平均每 (w + 1) / 2 个位置才输出一个指纹，将索引存储与查询开销压低一个数量级。工程上 SCANOSS .wfp 协议选用 gram = 30 字节、CRC32C 与 window = 64 作为默认参数，即是对索引体积与片段灵敏度的经典权衡。

警惕“全网克隆污染”与归属倒置（CENTRIS 核心洞察） 建一个全网开源指纹库后，新手立刻会遇到灾难性现象：当客户源码里包含了一段 zlib 函数，扫描器竟然一次性报出 400 个不同开源项目（因为这些项目当年都拷过 zlib）！更糟的是，如果某个热门框架（2019 年）也拷过 zlib（1995 年），扫描器往往把源头误归属成热门框架，或者把 A 和 B 同时报成嵌套重复依赖。

2.2 攻克 Type-3 魔改与嵌套拷贝：TLSH 局部敏感哈希 + CENTRIS 架构

为了既容忍 10%–30% 的代码改写，又解决上述“400 个仓同时误报与归属倒置”，我们借鉴 CENTRIS（ICSE 2021）（Centris-public）与 Trend Micro 开源的 TLSH（Apache-2.0 OR BSD-3-Clause 双宽松许可）设计三步精准溯源引擎：

  • ① 函数级分段 + TLSH 模糊哈希：传统加密哈希（SHA256）对 1 个字节改动也会雪崩失效；而 TLSH（Trend Micro Locality Sensitive Hash） 会生成固定长度的局部敏感指纹，允许直接计算两个函数体之间的距离分（Distance Score ≤ 30–50 判定为高度同源），天然抵抗 Type-3 删改与少量插入。
  • ② 跨仓库冗余消除（Redundancy Elimination）：在构建云端索引库前，按开源组件间的历史复用图剥离每个项目内部“拷贝自上游”的共享函数指纹，仅保留该组件独有特征函数（Unique Functions）用于主索引匹配。
  • ③ 最早诞生时间溯源（Birth-Time Attribution）：当多仓共享同一函数时，按 Git Commit 最早首次出现时间戳确立唯一源头组件（Original Owner），彻底杜绝把“下游拷贝者”错认成“上游原作者”，从而正确判定 CVE 与 GPL 许可证归属。

03无源码二进制 SCA：三层特征金字塔与商用许可排雷

3.1 Go 核心原语：Winnowing 局部指纹与二进制高 IDF 字符串评分器

无论是源码片段的 Zero-Source-Upload 本地指纹提取，还是穿透 strip -s 的字符串 TF-IDF 加权匹配，核心算法都极其干净，完全适合用 Pure Go 自研落地（无需引入任何 GPL C/Python 扫描器依赖）：

字符串指纹库为什么必须用 IDF 加权？ 假设你在某个静态链接的 ELF 里提取出字符串 "failed" 或 "out of memory"，它在全网 50,000 个开源库里都出现过（文档频率 DF 极高，逆文档频率 IDF ≈ 0），匹配它只会制造海量误报；而像 zlib 独有的报错串 "invalid literal/lengths set" 只在极少数版本家族中出现（IDF 极高），一旦在 .rodata 中同时命中 5–8 个高 IDF 特征串，即可实现 94%+ 置信度的精确组件定位。
Go 核心原语：Winnowing 本地指纹提取与二进制字符串 TF-IDF 归属评分 Pure Go 自研 L1 特征提取核心（Zero-Source-Upload & 穿透 strip -s） 
// 1. Schleimer Winnowing：在每个滑动窗口 w 中取最右最小哈希，保证检出任意 >= (w+k-1) 共享切片
func WinnowingFingerprints(tokens []string, k, w int) []uint32 {
    if k <= 0 || w <= 0 || len(tokens) < k {
        return nil
    }
    hashes := make([]uint32, 0, len(tokens)-k+1)
    for i := 0; i <= len(tokens)-k; i++ {
        h := fnv32a(strings.Join(tokens[i:i+k], " "))
        hashes = append(hashes, h)
    }
    if len(hashes) <= w {
        minIdx := 0
        for i := 1; i < len(hashes); i++ {
            if hashes[i] <= hashes[minIdx] { minIdx = i }
        }
        return []uint32{hashes[minIdx]}
    }

    var out []uint32
    lastPos := -1
    for start := 0; start <= len(hashes)-w; start++ {
        minIdx := start
        for j := start + 1; j < start+w; j++ {
            if hashes[j] <= hashes[minIdx] { // 并列最小时选最右，保证局部性
                minIdx = j
            }
        }
        if minIdx != lastPos {
            lastPos = minIdx
            out = append(out, hashes[minIdx])
        }
    }
    return out
}

// 2. 二进制 .rodata 字符串 IDF 倒排索引加权匹配（对齐 OSSPolice / B2SFinder）
type BinaryMatchCandidate struct {
    ComponentPURL string
    WeightedScore float64
    MatchedCount  int
    Confidence    float64
}

func ScoreBinaryStrings(extracted []string, idfTable map[string]float64, inverted map[string][]string, libTotalIDF map[string]float64) []BinaryMatchCandidate {
    scores := make(map[string]float64)
    hits := make(map[string]int)
    for _, s := range dedup(extracted) {
        idf := idfTable[s]
        if idf < 4.5 { // 过滤掉 "error" / "success" 等全网低区分度停用字符串
            continue
        }
        for _, purl := range inverted[s] {
            scores[purl] += idf
            hits[purl]++
        }
    }

    var results []BinaryMatchCandidate
    for purl, sc := range scores {
        conf := math.Min(0.98, sc/math.Max(1.0, libTotalIDF[purl]))
        if hits[purl] >= 3 && conf >= 0.45 {
            results = append(results, BinaryMatchCandidate{ComponentPURL: purl, WeightedScore: sc, MatchedCount: hits[purl], Confidence: conf})
        }
    }
    return results
}

3.2 同源与二进制 SCA 开源底座排雷矩阵（严守商用闭源 GPL 红线！）

代码同源与二进制逆向领域聚集了大量历史悠久的开源项目，但其中不少知名工具恰恰采用 GPL-2.0 / GPL-3.0 / LGPL-3.0 强传染性协议！选型时必须用手术刀级精度划分“可嵌入底座”与“严禁嵌入黑名单”：

开源项目 / 底座 精确许可证 核心工程能力 商业闭源架构边界与选型建议
lief-project/LIEF & Go debug/elf Apache-2.0 / BSD-3 跨平台统一解析 ELF / PE / Mach-O 节区、导出/导入表、动态依赖与 .rodata 段。 二进制 Layer A/B 首选底座：Go 原生服务先用标准库 debug/*，跨格式高级特性走 LIEF 隔离 Worker。
ReFirmLabs/binwalk (v3 Rust 重写) MIT 高速嵌入式固件熵分析与文件签名递归解包（SquashFS、U-Boot、LZMA 等）。 固件解包首选：v3 已全面重授权并重写为纯 Rust MIT，须跑在无特权沙箱内防止畸形固件 Zip/SquashFS 炸弹。
trendmicro/tlsh Apache-2.0 OR BSD-3-Clause 高鲁棒性局部敏感哈希（LSH），函数体删改 10%–30% 仍可通过距离阈值高效召回。 Type-3 函数同源核心组件：双宽松许可，可安心嵌入客户端指纹提取器与云端指纹库。
capstone & ghidra BSD-3-Clause / Apache-2.0 多架构反汇编框架（x86/ARM/MIPS/RISC-V）与企业级 Headless 反编译/P-Code CFG 提取。 Layer C 控制流图首选：纯宽松商用许可；Ghidra Headless 重资源，严禁进前端热路径，必须进异步 Tier 3 队列。
scanoss/wfp & scanoss/engine GPL-2.0 基于 Winnowing（30-byte CRC32C）的知名开源代码片段指纹提取器与匹配服务引擎。 严禁直接嵌入或打包分发！GPL-2.0 强传染；仅可学习其 Winnowing 算法与 .wfp 协议思想，用自研 Pure Go + Tree-sitter (MIT) 独立实现。
ossf/cve-bin-tool（原 Intel）& radare2 GPL-3.0-or-later / LGPL-3.0 cve-bin-tool 内置大量二进制版本签名匹配器；radare2 为逆向分析框架。 严禁嵌入闭源内核！cve-bin-tool 采用强传染 GPL-3.0；二进制逆向请选用纯 Apache-2.0 / BSD-3 的 LIEF + Capstone + Ghidra 组合替代 radare2。
