超越 CVSS：EPSS、CISA KEV 与 VEX（OpenVEX / CycloneDX / CSAF）协同降噪

在 Lesson 0011 与 Lesson 0012 中，我们用静动态融合把“代码/包是否可达”拆成了明确的四态结论。但在真实企业现场，即使只看可达漏洞，团队仍然面临“几百条中高危先修哪几条”以及“已证不可达的结论如何在 CI、安全审计与下游客户之间合法流转”两大难题。本课围绕总架构师与核心研发视角，拍板EPSS + CISA KEV + SSVC 非补偿决策树、三大 VEX 标准映射与统一不可变账本，以及Safety Floor 信任冲突裁决与事件驱动撤销机制。

本课收获：吃透 CVSS v4.0 vs EPSS v4（Probability ≠ Percentile）、CISA KEV（Floor 非 Ceiling）与 SSVC 非补偿树；掌握 OpenVEX / CycloneDX 1.7 / CSAF 2.0 语义映射与 subcomponents 作用域陷阱；落地纯 Apache-2.0 VEX 账本与事件撤销闭环 先修底座：Lesson 0002 · Lesson 0011 · Lesson 0012
架构师核心命题（对齐你的 MISSION.md）

第一代 SCA 靠 CVSS ≥ 7.0 一刀切，导致 80% 以上警报是死代码或永不被利用的噪音，却同时漏掉 CVSS 5.3 但正在被勒索软件大规模利用的 KEV 漏洞。第三代商业 SCA 的高溢价能力，是把 L4 可达性、实时威胁情报（EPSS/KEV）与标准化 VEX 证据链 拧成同一套“只叫对人修关键 5%”的决策引擎——既要压降噪音，更要扛住合规审计与 0-day 反扑。

01为什么 CVSS-B 与加权平均会制造“告警疲劳 + KEV 漏杀”

1.1 四套核心标尺的真实物理含义（严禁混用）

漏洞优先级设计中最大的工程错误，就是把“理论破坏力（Severity）”当成“现实风险（Risk）”。构建 Layer 4 优先级引擎前，必须先把四套权威标尺的正交边界钉死：

  • FIRST CVSS v4.0（CVSS-B vs CVSS-BT）：CVSS-B（Base Score）衡量的是漏洞在通用最坏假设下的固有技术严重性——如果未指定 Threat 维度，CVSS-B 默认按最坏威胁态（相当于存在主动攻击）计分；CVSS-BT 引入了离散的 Exploit Maturity（E:A / E:P / E:U），但它依然只是“有没有公开 PoC/攻击”的阶梯开关，无法回答统计概率。
  • FIRST EPSS v4（arXiv:2302.14172 演进）：Jay Jacobs 等人在 EPSS v3（IEEE EuroS&PW 2023，~1,500 维特征）基础上于 2025 年 3 月演进至 EPSS v4（强化恶意软件/勒索遥测、Shodan 与 HackerOne 等信号），每日输出每个 CVE 在未来 30 天内被真实在野利用的概率（0%–100%）。历史统计表明，全库超过 95% 的 CVE 利用概率贴近 0%。
  • CISA KEV Catalog（美国联邦公有领域可商用）：经过人工核验确认已经在野被攻击者实际利用的高置信度漏洞清单，标准 JSON 提供 8 个必填字段（cveID、vendorProject、product、vulnerabilityName、dateAdded、shortDescription、requiredAction、dueDate）及关键附加字段 knownRansomwareCampaignUse（取值为 "Known" 或 "Unknown"）。
  • CISA SSVC（Stakeholder-Specific Vulnerability Categorization）：由 CISA 与 CMU SEI 联合提出的非补偿性决策树，结合 Exploitation（Active/PoC/None）、Automatable（Yes/No）、Technical Impact（Total/Partial）与 Mission & Well-being，直接给出确定性动作输出：Act / Attend / Track* / Track。
工程避坑：EPSS Probability ≠ Percentile，KEV 是 Floor 非 Ceiling 坑 1 · 把 Percentile 当概率：EPSS API 同时返回 epss（绝对概率，如 0.004 = 0.4%）和 percentile（相对分位，如 0.58 = 超过 58% 的 CVE）。由于 90%+ CVE 几乎不被利用，第 60 百分位对应的绝对概率往往不到 0.5%！写阈值策略必须用 epss（Probability）而不是 percentile。
坑 2 · KEV 的滞后性与字段误读：KEV 具有天然滞后性（只收录已观测到实锤的少数漏洞），所以它是优先级底线（Floor）而非上限（Ceiling）——不在 KEV 不代表安全；同时 knownRansomwareCampaignUse: "Unknown" 只代表 CISA 暂未证实勒索关联，绝不等于“不会用于勒索”。
坑 3 · 同步查 API 与商业 ToS：严禁在扫描热路径逐条同步调用 api.first.org/data/v1/epss！后端必须每日定时拉取官方全量 gzip CSV 注入 Layer 3 内存/KV 索引，并严格遵守 FIRST Services Terms of Use（仅限漏洞披露与防御性安全用途，须保留版权署名，严禁脱离产品单独转售原始数据集）。

1.2 为什么“线性加权平均”是反模式？拥抱 SSVC 非补偿决策树

很多初创安全团队喜欢发明一个看似科学的多维打分公式：RiskScore = 0.3×CVSS + 0.25×EPSS + 0.2×KEV + 0.15×Reach + 0.1×Exposure。在决策论中，这种加法模型存在致命的补偿掩蔽（Compensatory Masking）问题：

  • 场景 A（死代码虚高）：某组件 CVSS 9.8 且 EPSS 62%，但 Layer 4 静态调用图与运行态已证 VERIFIED_UNREACHABLE（死代码）。线性加权仍会算出 6.5–7.2 的“高分”，迫使研发去修一条永远执行不到的代码。
  • 场景 B（低 CVSS KEV 被稀释）：某身份认证绕过漏洞因前置条件被评 CVSS 5.3，却已入选 CISA KEV 且直接挂载在公网网关上。线性加权被 0.3×5.3 拉低总分，错失 P0 阻断时机。

正确解法是将 Lesson 0011–0012 的 L4 可达性 与 CISA SSVC 非补偿决策树 做硬逻辑门控（Gating Logic）融合：

02VEX 三大标准（OpenVEX / CycloneDX 1.7 / CSAF 2.0）深度拆解与语义映射

2.1 VEX 不是“永久删告警”，而是可机器校验的“影响状态声明”

当 Layer 4 证明了某个组件在特定应用中 VERIFIED_UNREACHABLE，或者某上游安全团队已经通过本地热补丁修复了漏洞，传统的做法是在扫描器 UI 里点一下 Ignore——这种黑盒操作无法跨工具链流转，更过不了金融、车企或政企客户（如欧盟 CRA、美国联邦采购）的合规审计。VEX（Vulnerability Exploitability eXchange）就是用来解决“SBOM 之外的漏洞可达性与影响声明交换”的开放标准。

目前全球供应链形成三大主流 VEX 载体，它们共享 CISA Minimum Requirements for VEX 的核心语义，但数据结构与适用场景截然不同：

  • OpenVEX（Apache-2.0 · OpenSSF / Chainguard 主导）：极简、与 SBOM 格式解耦的 JSON-LD 流式声明模型，原生支持将签名后的 VEX 作为 OCI 1.1 Referrers 附着在容器镜像旁随镜像流转（Trivy --vex oci / vexctl），是云原生与 CI/CD 内部交换的最佳默认格式。
  • CycloneDX 1.6 / 1.7（ECMA-424）：组件为中心，把 vulnerabilities[].analysis 直接内嵌在 SBOM 中（此时充当 VDR 漏洞披露报告）或导出为独立 VEX 文件。支持最细粒度的状态（含 resolved_with_pedigree 与扫描器误报专用态 false_positive）。
  • OASIS CSAF 2.0 VEX Profile（csaf_vex）：安全公告（Advisory）中心，以复杂的 product_tree 绑定多个产品版本家族，被 Red Hat、Cisco、Siemens 及欧洲监管机构（BSI）广泛采用。
必纠概念：VDR vs VEX 与 false_positive 语义红线 1. VDR ≠ VEX：VDR（Vulnerability Disclosure Report）是随软件发布的“全量已知漏洞台账+处置计划”；VEX 只回答“某个漏洞在特定产品上下文是否受影响”。
2. 严禁滥用 false_positive：在 CycloneDX 中，false_positive 专指扫描器识别错了包/版本（例如把同名私包或误报正则匹配成了上游库）；如果产品确实包含了该漏洞组件只是调用路径不可达，必须使用 not_affected + code_not_reachable！OpenVEX 没有 false_positive 状态，同样统一归入 not_affected 并注明理由。

2.3 OpenVEX subcomponents 作用域陷阱与 Canonical VEX Ledger

在真实容器与微服务场景下，签发 VEX 最容易埋下全局失明雷坑的就是PURL 作用域缺失：假设某团队发现镜像 A 中的 golang.org/x/oauth2@v0.18.0 某个函数不可达，如果在 VEX 的 products 中直接把 @id 写成裸库 pkg:golang/golang.org/x/oauth2@v0.18.0，那么当这个库被镜像 B 的高危支付接口真实调用时，全局消费该 VEX 的扫描器就会把镜像 B 也一起静默掉！

正确的做法（也是 Trivy OpenVEX 规范 强制推荐的方式），是利用 OpenVEX 的 products[].subcomponents[] 双层锚点：外层 @id 锁定具体的应用制品或容器摘要（pkg:oci/checkout-api@sha256:...），内层 subcomponents[] 才写具体的脆弱三方库 PURL，确保豁免严格局限在“经过实证的特定容器/二进制边界内”。

03企业级 VEX 信任层级、冲突裁决（Safety Floor）与事件驱动撤销

3.1 当社区 VEX Hub 声称“不受影响”，而你方调用图显示“可达”时信谁？

随着 Aqua 推出 VEX Hub 以及各大开源项目开始随包分发 VEX，平台很快会面临多方 VEX 冲突：例如上游开源维护者发了一份 OpenVEX 声明“not_affected”（因为该组件默认配置不触发），但你方客户在业务代码里偏偏开启了那个危险选项，且 Lesson 0011–0012 已捕获到了真实调用链。

参考 Trivy --vex 的显式优先级链设计（命令行最先传入的源优先级最高，例如 --vex local.json --vex oci --vex repo）与商业 SCA 零漏报红线，平台必须建立不可逾越的四级 VEX 信任层级与安全底线（Safety Floor）：

  1. Tier 0 · Hard Evidence Safety Floor（不可推翻的硬实证底线）：只要本平台 L4 捕获到 CONFIRMED_EXPLOITABLE、REACHABLE 或生产 EXECUTED_FUNC，任何外部或历史 VEX not_affected 声明一律被强行驳回，触发 VEX_CONFLICT_OVERRIDE 告警。
  2. Tier 1 · 本平台实证签发 / 组织内审签名 VEX（internal_verified）：附带本仓库 Call Graph 摘要或已签名人工缓解审批（且未过 TTL）。
  3. Tier 2 · 上游厂商密码学签名 VEX（vendor_signed）：通过 Sigstore/PGP 验签的原厂 CSAF/OpenVEX（如 Red Hat 对自有 RHEL Backport 的声明），且要求产品 PURL 与版本精确命中。
  4. Tier 3 · 社区未签名 VEX Hub（community_unsigned）：仅用于“降级标注与人工参考提示”，严禁在没有 L4 静态/动态印证的情况下直接自动阻断 P0 告警或屏蔽 KEV 漏洞。
VEX 必须具备“事件驱动自动撤销”机制 任何 not_affected 结论只在特定时间切片与拓扑下成立。参考 OpenVEX 的时间线覆盖原则（同产品+漏洞下最新时间戳/版本语句覆盖旧语句），平台必须监听五大撤销触发器：
① 代码提交改变 Call Graph 连通性；
② JFR/eBPF 在生产抓到原判不可达类的加载；
③ 漏洞新入 CISA KEV（强制复核潜伏与人工缓解项）；
④ EPSS 7 日内飙升 ≥ +20%；
⑤ 人工缓解型 VEX（inline_mitigations_already_exist）强制设置的 30–90 天 TTL 到期。
Go 核心原语：SSVC 非补偿裁决器、Safety Floor 冲突拦截与 VEX 事件撤销校验 Pure Go 自研核心（可无缝对接 go-vex / cyclonedx-go / gocsaf） 
type SSVCAction string
const (
    ActionAct    SSVCAction = "Act"    // P0: 24h-72h 紧急阻断与自动 PR
    ActionAttend SSVCAction = "Attend" // P1/P2: 7d-14d 常规迭代修复
    ActionTrackS SSVCAction = "Track*" // P3: 增强监控 EPSS/KEV 异动
    ActionTrack  SSVCAction = "Track"  // P4: 已证不可达或 VEX 生效豁免
)

type TriageInput struct {
    CVSSBase          float64
    EPSSProb          float64 // 注意：必须用 Probability (0.0-1.0)，绝不用 Percentile!
    InCISAKEV         bool
    RansomwareKnown   bool
    ReachState        string  // CONFIRMED_EXPLOITABLE | REACHABLE | LATENT_REACHABLE | VERIFIED_UNREACHABLE
    InternetExposed   bool
    ExternalVEXStatus string  // "" | "not_affected"
    VEXTrustTier      int     // 1:InternalVerified, 2:VendorSigned, 3:CommunityUnsigned
    VEXExpired        bool
}

func EvaluatePriorityAndVEX(in TriageInput) (SSVCAction, string) {
    hardReachable := in.ReachState == "CONFIRMED_EXPLOITABLE" ||
        in.ReachState == "REACHABLE" || in.ReachState == "LATENT_REACHABLE"

    // 1. Safety Floor：硬可达实证拥有最高否决权，直接驳回外部/社区 VEX 豁免
    if hardReachable && in.ExternalVEXStatus == "not_affected" {
        emitVexConflictAlert(in)
        return ActionAct, "REJECTED_VEX_CONFLICT"
    }
    // 2. 静动态双证不可达 -> 压降为 Track 并可安全签发带子组件作用域的 VEX
    if in.ReachState == "VERIFIED_UNREACHABLE" {
        return ActionTrack, "ISSUE_INTERNAL_VEX_NOT_AFFECTED"
    }
    // 3. KEV 或高 EPSS 命中非补偿 Act 路径（无视 CVSS 是否低于 7.0）
    if in.InCISAKEV || (in.ReachState == "CONFIRMED_EXPLOITABLE" && (in.EPSSProb >= 0.20 || in.InternetExposed)) {
        return ActionAct, "VEX_PROHIBITED"
    }
    // 4. 校验有效 VEX（仅 Tier 1/2 且未过 TTL 才允许生效消噪）
    if in.ExternalVEXStatus == "not_affected" && !in.VEXExpired && in.VEXTrustTier <= 2 {
        return ActionTrack, "VALID_EXTERNAL_VEX"
    }
    // 5. 低 EPSS 护栏：LATENT_REACHABLE / REACHABLE 绝不因 EPSS 低而豁免
    if hardReachable {
        return ActionAttend, "NO_AUTO_VEX_LOW_EPSS_GUARD"
    }
    return ActionTrackS, "WATCHLIST_EVENT_REVAL"
}
