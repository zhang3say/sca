01为什么「单靠 NVD」已死，而「整包搬运 OSV」也会触法？

第一代 SCA 产品的漏洞底座设计极其朴素：同步一份 NIST NVD JSON Feed，把待扫组件猜成 CPE 字符串去碰版本区间。然而到了 2024–2026 年，这条单源路径已在技术与组织双维度彻底失效：

  • NVD 结构性滞后与 CPE 断点：自 2024 年初爆发积压危机以来，NIST NVD 转向风险优先级分诊——大量开源与常规漏洞长期处于 Awaiting Analysis 或直接标记为 Not Scheduled，导致超过半数新 CVE 长期缺失 CPE 与 CVSS 映射。纯靠 NVD 的扫描器会大面积静默漏报。
  • CPE 命名失真：正如 Lesson 0002 拆解，CPE 缺乏生态命名空间（如无法区分 PyPI 包与同名商业软件），即使老漏洞补上了 CPE，也极易触发跨厂商碰撞误报。

于是许多团队转向另一个极端：“既然 Google 已经做好了 OSV.dev，我直接把 gs://osv-vulnerabilities/all.zip 下载打包进商业产品里卖不就行了？”——这是商业闭源产品极易踩中的法务深坑！

开源代码许可 ≠ 漏洞数据许可 google/osv.dev 与 anchore/vunnel 的程序源码都是 Apache-2.0，但漏洞库里每一条记录的数据版权归属于各自上游源！根据 OSV.dev 官方数据源文档，里面混杂着 CC0、CC-BY-4.0、CC-BY-SA-4.0 甚至严禁商业扫描器打包分发的 CC-BY-NC-ND-4.0！

02OpenSSF OSV Schema 1.7.0 拆解与「三元关系图」去重模型

尽管数据源许可需要隔离，数据格式标准化上必须坚定采纳 OpenSSF OSV Schema（v1.7.0，2025-03 发布） 作为平台 Layer 3 的统一入库契约。它用三条核心设计解决了 CVE/CPE 时代二十年的痛点：

  1. 直接锚定包坐标与版本事件流：每个 affected[] 元素直指 package (ecosystem, name, purl)，版本区间由按时间演进的 ranges[].events[]（introduced / fixed / last_affected / limit）配合 SEMVER / ECOSYSTEM / GIT 三类比较语义表达（"introduced": "0" 代表从创世首版起即受影响）。
  2. 扩展隔离双槽位：标准之外的原生信号（如 Go 的受影响函数列表 imports[].symbols，这正是 Phase 2 可达性剪枝的燃料！）放入 ecosystem_specific；各库私有评分或审查标签放入 database_specific。
  3. 显式撤销墓碑（withdrawn）：一旦某条 CVE 或虚假通告被撤销，上游保留记录并写入 RFC 3339 withdrawn 时间戳，而非静默删库——下游扫描器才能识别并收敛历史告警。
v1.7.0 必知新增字段 OSV v1.7.0 除了支持 CVSS_V4 严重度向量外，最关键的架构升级是正式引入了 upstream[] 字段，专门解决发行版 Backport 通告与上游 CVE 的层次污染难题（见下文 2.1）。

2.1 去重命门：aliases vs upstream vs related 的严格语义边界

同一件漏洞往往同时拥有 CVE-2024-21626、GHSA-xr7r-f8xq-vfvv、GO-2024-2491、Debian DSA-5615-1 和 Ubuntu USN-6619-1。做多源汇聚时，初学者最常犯的致命错误，就是把所有关联编号全塞进一个 aliases 数组做等价聚类！

参考 OSV 官方 upstream 设计解析 与 Google deps.dev 图模型，Layer 3 必须将关系严格拆分为三种不同语义的图谱边：

  • aliases（对称等价闭包，ALIAS_OF）：仅用于描述完全相同的底层漏洞、同一受影响源码体与同一上游补丁（如 GHSA-xr7r-f8xq-vfvv ↔ CVE-2024-21626 ↔ GO-2024-2491）。等价组在报告层合并计数，也可共享未修区间校验。
  • upstream（有向衍生链，UPSTREAM_OF）：当下游发行版（如 Debian DSA-5615-1、Ubuntu USN-6619-1）针对旧版本做 Backport 修复时，修复版本号与上游截然不同（Debian 的 1.1.5+ds1-1+deb12u1 字符串上仍小于上游修复版 1.1.12！）。此时只能由发行版通告通过 upstream 指向根 CVE，绝对禁止写入 aliases——否则等价传递闭包会把上游的 < 1.1.12 规则传染给 Debian 容器，引爆海量误报！
  • related（弱关联参考，RELATED_TO）：同根因但独立影响不同组件或拆分为多补丁的关联条目（如同一批披露的多个 SSRF CVE），仅作 UI 关联跳转，既不合并计数也不共享版本区间。
开源前车之鉴：Dependency-Track 与 Grype Dependency-Track 早期未分离强等价与弱关联时，若全盘同步 OSV 别名容易导致告警组异常膨胀（官方甚至默认谨慎开启 OSV 别名全同步）；而 Anchore Grype 的 --by-cve 早期在 Go Map 遍历合并相同 CVE 的 GHSA/NVD 记录时曾因缺少确定性权威排序出现结果摇摆。自研底座必须从第一天就用有向图边类型 + 确定性仲裁优先级封死这两个坑！

03自研 Layer 3 汇聚引擎：借鉴 Vunnel 解耦 + 分字段权威裁决矩阵

在开源参照上，Anchore Vunnel（Apache-2.0） 示范了极好的多源 ETL 解耦形态：每个上游源（NVD、GHSA、Debian、RHEL、Alpine 等）封装为独立的 Provider 插件拉取并落盘到隔离的 Workspace，再由下游构建器组装成匹配库。但直接拿 vunnel + grype-db 充当商业底座存在两点不足：① 默认没有商业闭源所需的数据许可准入闸门；② 缺少精细到字段级别的多源覆盖仲裁与持续重算事件通知。

因此我们的绿地架构采用「Provider 隔离采集（借鉴 Vunnel/OSV） + 自研 Layer 3 规范化与分字段裁决器（Arbiter）」四段流水线：

黄金铁律：Raw 永不覆盖，Arbiter 分字段合成 当同一个 CVE-2024-XXXX 同时来自 NVD、CVEListV5 与 GHSA 时，不要做“谁权重高就整条覆盖掉谁”。正确的做法是在 raw_advisories 表完整保留多源原始快照，然后由 Arbiter 按字段维度独立取优合成一张干净的规范视图（Canonical Advisory）。
Layer 3 核心持久化 Schema（PostgreSQL）：原始快照隔离 + 关系图边 + 权威裁决匹配规则 PostgreSQL · 兼顾多源回溯、许可审计与防误报隔离 
-- 1. 多源原始情报仓：绝不互相覆盖，强制绑定数据许可与审查等级
CREATE TABLE raw_advisories (
  source_id         TEXT NOT NULL,          -- 'ghsa_reviewed' | 'ghsa_unreviewed' | 'nvd' | 'cvelistv5' | 'debian_dsa' | 'pypa'
  external_id       TEXT NOT NULL,          -- 'GHSA-cvq5-hhx3-f99p' | 'CVE-2026-22039' | 'DSA-5615-1'
  data_license      TEXT NOT NULL,          -- 'CC0-1.0' | 'CC-BY-4.0' | 'CVE-TOU' (Gate 已拒绝 NC/ND)
  review_tier       SMALLINT NOT NULL,      -- 100=生态官方/Reviewed, 70=CNA/ADP, 50=NVD, 20=Unreviewed
  lifecycle_state   TEXT NOT NULL,          -- 'ACTIVE' | 'WITHDRAWN' | 'REJECTED'
  withdrawn_at      TIMESTAMPTZ,
  osv_payload       JSONB NOT NULL,         -- 归一化为 OSV v1.7.0 JSON
  payload_sha256    TEXT NOT NULL,
  PRIMARY KEY (source_id, external_id)
);

-- 2. 漏洞三元关系边：严禁把 UPSTREAM_OF 混入 ALIAS_OF 传递闭包
CREATE TABLE advisory_edges (
  src_id            TEXT NOT NULL,
  dst_id            TEXT NOT NULL,
  edge_type         TEXT NOT NULL CHECK (edge_type IN ('ALIAS_OF', 'UPSTREAM_OF', 'RELATED_TO')),
  evidence_source   TEXT NOT NULL,
  PRIMARY KEY (src_id, dst_id, edge_type)
);

-- 3. 裁决后编译的规范匹配规则（供 Lesson 0008 版本引擎与 0009 离线索引直接消费）
CREATE TABLE canonical_match_rules (
  rule_id           UUID PRIMARY KEY,
  canonical_group   TEXT NOT NULL,          -- ALIAS_OF 连通分量主 ID
  rule_scope        TEXT NOT NULL,          -- 'UPSTREAM_PKG' | 'DISTRO_BACKPORT' | 'CPE_FALLBACK'
  base_purl         TEXT NOT NULL,          -- 如 'pkg:golang/github.com/kyverno/kyverno'
  distro_qualifier  TEXT DEFAULT '',        -- 非空时仅匹配对应发行版（如 'debian-12'）
  range_type        TEXT NOT NULL,          -- 'SEMVER' | 'ECOSYSTEM' | 'GIT'
  events_json       JSONB NOT NULL,         -- [{"introduced":"1.16.0"},{"fixed":"1.16.3"}]
  authority_source  TEXT NOT NULL,          -- 胜出权威源，用于追溯与审计
  is_enabled        BOOLEAN NOT NULL DEFAULT true -- WITHDRAWN 时置 false
);
商业标杆 Snyk VulnDB 给我们的长期演进启发

为什么企业客户愿意为商业漏洞库付溢价？Snyk VulnDB 的核心差异化并不在于“搬运 CVE 更快”，而在于两点自研增值：① Non-CVE 早期情报与精准区间修复（Curation）——安全研究员把 NVD/GHSA 里写错的区间、缺失的包名修正，并补上非 CVE 的恶意/高危漏洞（SNYK-*）；② 可消费的上下文字段——在每条记录上附带受影响函数签名与修复升级路径。我们今天搭好的 raw_advisories → Field Arbiter → canonical_match_rules 分层，未来只需在最高优先级增加一层 internal_curation（权重 review_tier = 200），就能平滑长出对标商业标杆的自研研究团队覆写能力，无需改动一行业务查询代码！
