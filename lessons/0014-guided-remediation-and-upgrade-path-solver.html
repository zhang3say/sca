无破坏性自动修复与升级路径求解器（Guided Remediation）

经过 Lesson 0011–0013 的静动态可达性过滤与 SSVC/VEX 协同降噪，我们已经把 1,000 条噪音漏洞浓缩为 30 条真正该修的 Act / Attend 队列。但若在“最后一公里”退回传统扫描器“发现一个 CVE 就盲目发一个单包升级 PR”的做法，研发团队会立刻被 PR 风暴（PR Fatigue） 与构建崩毁淹没。本课作为 Chapter 04 收官，带你设计多目标图约束求解器、API Diff ∩ 第一方调用图 零破坏升级影响引擎，以及面向人类与 AI Coding Agent 的双触点自愈闭环。

本课收获：吃透 OSV-Scanner v2 三大策略（in-place / relock / override）与 PubGrub 求解边界；落地基于 Ochoa 实证与 japicmp/apidiff/griffe 的 Safe Major 交集引擎；掌握 OpenRewrite LST 与 AGPL-3.0 Renovate 避坑及双触点交付 先修底座：Lesson 0003 · Lesson 0010 · Lesson 0011 · Lesson 0013
架构师核心命题（对齐你的 MISSION.md）

第一代修复机器人只是“版本号搬运工”——把锁文件里每个漏洞包单点替换成最新补丁号，既不管上层父依赖是否兼容，也不管新版本是否换成了 AGPL-3.0 或引入新 CVE。第三代商业 SCA（如 Snyk Remediation Graph、Endor Labs Upgrade Impact、Google OSV-Scanner v2）的真正壁垒，是把修复重构升级为基于依赖图 + 许可证 + 调用图破坏面交集的多目标帕累托求解问题：用最少个数的 PR，零破坏地拔除最多真实风险，并能在 AI Agent 本地写代码阶段直接通过 MCP 完成自愈。

01为什么“单包无脑升级”会制造 PR 风暴与构建崩毁？—— 三大策略与图求解模型

1.1 拆解 Google OSV-Scanner v2 Guided Remediation 三大修复策略

在现代传递依赖占 80% 以上的软件供应链中，一个漏洞往往藏在 3–5 层深的传递包里。参考 Google OSV-Scanner Guided Remediation（osv-scanner fix） 与 deps.dev/util/resolve 的图求解架构，自动修复必须区分风险与收益截然不同的三种修改策略：

  • ① in-place（原位锁文件更新）：严格遵守当前 Manifest（如 package.json）既有的语义版本区间，仅原地重写 Lockfile（package-lock.json）中可向上滑动的传递依赖节点。优点：变更面最小、几乎不改变直接依赖约束；局限：一旦修复版本落在 Manifest 区间之外（例如被 ^2.14.0 锁死而安全版在 3.0.4），原位策略直接无解。
  • ② relock / relax（放宽并重算直接依赖）：允许突破 Manifest 的版本上下界，向上升级顶层直接依赖（Direct Dependency）并重新计算整棵依赖子树，从而顺带把深层多个脆弱传递依赖一并“冲洗”出图。配合 --upgrade-config（限制 Patch / Minor / Major）、--min-severity 与 --max-depth，可以把“升级几个直接包”转化为最大 ROI 排序问题。
  • ③ override（强行传递依赖覆写）：典型用于 Java Maven <dependencyManagement> 或 npm overrides，在不升级直接父依赖的前提下，强行把深层传递依赖钉死到安全版本。

数学上，Guided Remediation 求解器并非贪心寻找“单一最低修复版”，而是在候选升级向量 \(X = \{d_1 \to v_1', \dots, d_k \to v_k'\}\) 上求解多目标帕累托最优：同时最小化「直接依赖变更数」「语义版本距离（Patch < Minor < Major）」「真实业务调用破坏点数」，并最大化「消除的 Act / Attend 漏洞数」，且硬性约束零许可证传染漂移 & 零高危新 CVE 回归。

工程红线：Override 隐形定时炸弹与沙箱隔离 坑 1 · override 的运行期崩毁陷阱：当中间父依赖（如 reactor-netty）硬绑定了传递库 netty@4.1.x 的内部构造方法时，用 Maven <dependencyManagement> 强行 override 跨大版本至 4.2.0，主工程源码本身不直接调 Netty 所以往往编译通过，一到线上流量路径就抛出 NoSuchMethodError！因此商业求解器必须在优先度上遵循 in-place → relock (直接父包) → 带中间父包字节码校验的受控 override。
坑 2 · 重锁执行的供应链投毒风险：osv-scanner fix 等重锁工具一旦调用原生包管理器解析依赖，可能触发 npm postinstall 或 Maven 插件下载。与 Lesson 0003 一致，所有 relock 解析严禁在宿主机热路径裸跑，必须进入无特权、无宿主机密钥的 Tier 3 沙箱（如配 --ignore-scripts）。

1.2 跨生态依赖图求解算法与锁文件重写规范

不同包生态的依赖解析语义差异巨大，统一修复求解器绝不能把 npm 的树形嵌套逻辑套用到 Python 或 Go 上。下表是 Layer 4 修复引擎跨四大主力生态的核心求解契约：

语言生态 底层求解算法 / 核心引擎 支持策略与文件改写锚点 工程避坑与商用许可边界
JavaScript / npm deps.dev/util/resolve（Apache-2.0）+ 最大版本号优先匹配 in-place（package-lock.json）与 relock（package.json + lock）；支持嵌套重复依赖独立去重。 注意同库多版本共存（Diamond 保留双副本）时，单测“仅修其中一个路径”会残留另一副本的漏洞！
Java / Maven & Gradle deps.dev Effective POM 解析 + Nearest-Wins 树裁决 + OpenRewrite LST 支持 relock 直接父依赖与 override（注入 <dependencyManagement> 或 Gradle constraints）。 必须检查 Multi-Module 父 POM <properties> 变量占位符，禁正则硬替换破坏 XML 格式与注释。
Python (uv / Poetry) PubGrub（Dart pub / pubgrub-rs CDCL 冲突驱动子句学习） 支持多平台标记（sys_platform / python_version）与全局单版本约束求解并生成人类可读冲突解释。 MPL-2.0 注意：pubgrub-rs 为 MPL-2.0（文件级弱传染），若修改其 Rust 源码须开源该文件，推荐以独立 Crate/Worker 边界引用。
Go Modules 官方 MVS（Minimal Version Selection）确定性最小版本选择 go.mod 显式升顶层 require + go mod tidy（对 v2+ 主版本须同步改写 import path）。 MVS 天然偏爱满足约束的最小版本而非盲目最新版，天然契合“最小扰动升级”哲学。

02超越 SemVer 盲猜——“API Diff ∩ 第一方调用图”的升级影响分析

2.1 来自 29 万客户端的实证反转：库有破坏性变更 ≠ 你的业务会崩

第一代与第二代修复工具在面对跨 Major 升级（例如 2.14.3 → 3.0.4）时几乎全部选择“躺平”——仅凭主版本号变更就标为“高破坏风险”不敢动，导致大量跨大版本的 KEV 漏洞在企业仓库里一躺就是两年。

但学术界与工业界的大规模实证彻底推翻了这种粗糙假设。Lina Ochoa 等人在 Empirical Software Engineering（2022，DOI 10.1007/s10664-021-10052-y）发表的标杆研究，利用静态字节码分析工具 Maracas 横向实测了 Maven Central 约 120,000 次库升级 与 293,000 个下游客户端应用，揭示了两条决定第三代 SCA 架构设计的铁律：

  • 铁律 A（高 SemVer 遵从下的低真实波及率）：约 83.4% 的库升级遵守了 SemVer 规范；更重要的是，即便升级包含了破坏性 API 变更，由于绝大多数破坏发生在客户端根本没调到的边缘公开方法或内部类上，最终实际受到破坏性变更波及的客户端仅占约 7.9%（超过 92% 的客户端其实安然无恙）！
  • 铁律 B（非 Major 升级的暗雷不可忽视）：仍有约 16.6% 的库升级存在 SemVer 违规（在 Minor/Patch 中悄悄删改签名或破坏行为），单纯迷信“Patch/Minor 一定安全”同样会导致 CI 爆炸。
第三代核心公式：Upgrade Impact Analysis 真实破坏面 = BreakingSymbols(v_old → v_new) ∩ ReachableUsedSymbols(App, Lib)
• 若交集为 ∅（0 命中），即使从 2.x 升到 3.x 也是 Safe Major——随 PR 附上调用图零命中证明，研发合并率飙升至 90%+！
• 若交集 非空（命中具体文件与行号），精确标注 OrderService.java:142 供 OpenRewrite LST 或 AI Coding Agent 精准改写，彻底消灭盲猜。

2.2 工程落地：云端离线预计算 API Diff + 在线毫秒级调用图求交

与 Lesson 0011 的云端函数摘要缓存同构，升级影响分析绝不能在 PR 扫描热路径现拉两个版本的源码/JAR 现算 Diff。正确架构是两段式解耦：

  1. 云端异步预计算（L3/L4 Artifact Diff Cache）：按 (purl, v_old, v_new) 键对热门开源包版本跃迁离线提取公开符号破坏集合（移除类/方法、签名变更、参数收缩、访问级别收窄及中间父依赖兼容断点），写入分布式 KV 索引。
  2. PR / Agent 在线毫秒级求交：直接复用 Lesson 0011 已生成的第一方应用调用图 ReachableUsedSymbols(App)，在内存中与预计算集合做集合求交（O(|Used|)），毫秒级判定该升级候选属于 ZERO_BREAKING（安全放行）还是 TARGETED_BREAKING(sites[])。
语言生态 推荐开源 API Diff 引擎 精确许可证 核心检测能力与商业闭源边界（务必验清同名项目！）
Java / JVM siom79/japicmp · revapi/revapi Apache-2.0 直接对比新旧 .jar 字节码，精确识别二进制/源码不兼容变更（删除方法、改返回值、抛新受检异常、改接口默认方法）；纯 Apache-2.0 可直接嵌入分析服务。
Go golang.org/x/exp/apidiff BSD-3-Clause 基于 Go go/types 校验导出类型、结构体字段、函数签名及方法集兼容性；严禁与 OpenJDK Code Tools 同名工具 apidiff（GPL-2.0 + Classpath）混淆！
Python mkdocstrings/griffe ISC 基于 AST 静态提取模块/类/函数签名、关键字参数、默认值与类型注解并内置 Breaking Change 规则引擎；ISC 等价 MIT，无任何传染限制。
Rust cargo-semver-checks MIT OR Apache-2.0 消费 rustdoc JSON 语义模型运行上百条 SemVer 破坏性 lint；注意 rustdoc 需进 Tier 3 沙箱防止 build script 越权执行。
TypeScript / JS TypeScript Compiler API Apache-2.0 比对公开 .d.ts 类型声明树（导出符号删除、必选参数新增、联合类型收窄），并与 Lesson 0011 的 Jelly 调用边求交。

03无损改写、双触点闭环与商用开源底座排雷

3.1 Go 核心原语：多目标求解、三重回归刹车与双触点计划生成

在我们的四层架构中，依赖求解调度、三重安全刹车（许可/新 CVE/中间父包 ABI）、调用图影响交集裁决与防 PR 风暴聚合逻辑属于平台的核心差异化资产，必须以 Pure Go 自研稳控在 Layer 4；底层锁文件改写与代码重构则封装 Apache-2.0/MIT 引擎输出。

企业级防 PR 风暴 4 条工程铁律 ① 仅修 Act / Attend：死代码 Track 已被 VEX 消噪，绝不发 PR 骚扰研发；
② 按顶层直接依赖聚合：1 棵直接依赖下的 6 条传递 CVE 合并为 1 个聚合 PR；
③ 单仓并发上限（默认 3–5 个）：超额进入排序缓冲池，合并一个再放行下一个；
④ Agent 优先本地自愈：当存在非零业务代码破坏点时，通过 MCP/Hook 直接把调用点和迁移方案交给 Coding Agent 本地改代码并跑单测，远比往 Git 推一个“编译失败的红灯 PR”优雅得多。
Go 核心原语：Guided Remediation 多目标求解、三重安全刹车与双触点计划 Pure Go 自研核心（对接 deps.dev/util/resolve · API Diff Cache · OpenRewrite/MCP） 
type RemediationStrategy string
const (
    StrategyInPlace RemediationStrategy = "in-place"
    StrategyRelock  RemediationStrategy = "relock"
    StrategyOverride RemediationStrategy = "override"
)

type UpgradeCandidate struct {
    DirectRootPURL     string              // 聚合后的顶层直接依赖（非裸传递子包）
    FromVer, ToVer     string
    Strategy           RemediationStrategy
    SemverSpan         int                 // 1:Patch, 2:Minor, 3:Major
    FixedVulnIDs       []string            // 本次顺带拔除的全部 Act/Attend 漏洞
    IntroducedNewCVEs  []string            // 升级后引入的新高危或 KEV 漏洞（必为 0）
    LicenseViolations  []string            // 新增 GPL/AGPL 等红线许可证（必为 0）
    ParentABIConflicts []string            // override 时中间父包字节码签名冲突点
    BreakingCallSites  []string            // API Diff ∩ 第一方调用图真实命中的 file:line
}

type RemediationPlan struct {
    Candidate      UpgradeCandidate
    AutoMergeSafe  bool   // 仅当 BreakingCallSites == 0 且三重刹车全绿时为 true
    HumanPRSummary string // 人类侧 PR 说明 + OpenRewrite LST 配方引用
    AgentMCPAction string // Coding Agent 侧 sca_plan_remediation 结构化修改指令
}

func SelectOptimalRemediationPlans(cands []UpgradeCandidate, maxOpenPRs int) []RemediationPlan {
    var valid []UpgradeCandidate
    for _, c := range cands {
        // 三重硬性安全刹车：新 CVE 回归、许可证传染漂移、Override 撕裂中间父包 ABI 一票否决
        if len(c.IntroducedNewCVEs) > 0 || len(c.LicenseViolations) > 0 || len(c.ParentABIConflicts) > 0 {
            continue
        }
        valid = append(valid, c)
    }

    // 多目标帕累托排序：1) 业务破坏调用点最少  2) 消除漏洞最多  3) 版本跨度最小  4) 优先 in-place/relock
    sort.Slice(valid, func(i, j int) bool {
        if len(valid[i].BreakingCallSites) != len(valid[j].BreakingCallSites) {
            return len(valid[i].BreakingCallSites) < len(valid[j].BreakingCallSites)
        }
        if len(valid[i].FixedVulnIDs) != len(valid[j].FixedVulnIDs) {
            return len(valid[i].FixedVulnIDs) > len(valid[j].FixedVulnIDs)
        }
        return valid[i].SemverSpan < valid[j].SemverSpan
    })

    // 单仓并发限流（防 PR 风暴）并生成人类 + AI Agent 双触点交付载荷
    return buildDualTouchpointPlans(valid, maxOpenPRs)
}

3.2 自动修复与重构开源底座选型矩阵（警惕 Renovate AGPL-3.0 陷阱！）

很多初创团队一做自动发 PR 功能就想把开源界功能最全的 Renovate 直接打包进自己的商业 SaaS 平台——这是典型的致命合规地雷。下表严格界定了自动修复领域各标杆项目的许可证与商用边界：

google/osv-scanner & deps.dev Apache-2.0 提供 osv-scanner fix 策略架构与 deps.dev/util/resolve Go 跨生态图求解核心，直接对齐 OSV 漏洞格式。 首选 Go 求解底座：直接库级集成求解核心至平台 Layer 4，配合 Tier 3 沙箱安全重锁。
