全场景 SCA 产品域模型、五类角色旅程与核心闭环编排

学完前 22 课，你已经拥有 L1–L4 全栈引擎原理与「一核三阶」商业分层蓝图；但真正打开 IDE 建表写代码前，80% 的绿地 SCA 项目会栽在同一个坑里——直接把“单次 SBOM 扫描结果”当成数据库主业务模型。本课为「1 人 + AI Agent」双模产品立下第一块工程基石：8 层产品域对象契约、五类角色 4 条端到端闭环，以及一套代码同时跑通 SaaS 订阅与离线私有化开关的 OpenFeature Entitlement 网关。

本课收获：划清 Layer 2 IR（技术事实层）与产品域台账（业务治理层）的边界；拍板 Snapshot × LogicalFinding × ReleaseBundle 三分离结构；掌握用 CNCF OpenFeature（Apache-2.0）统一双模商业能力开关 前置关联：Lesson 0002 (Layer 2 IR) · Lesson 0013 (VEX) · Lesson 0022 (一核三阶 SKU)
Solo + AI Agent 研发第一铁律：先锁死域模型，再让 AI 写代码

AI Coding Agent 最擅长在清晰的实体关系与接口契约内高速生成 Go/Python 代码，但也最容易在“领域边界模糊”时造出两套打架的表结构——比如把人工豁免直接塞进每次扫描生成的 JSON 里。把 8 个核心业务实体的主键、不可变性与生命周期写进第一天的数据模型，后续无论是加 AI-BOM、做 0-day 夜间重算，还是导出欧盟 CRA 封板证据，都不必推倒重来。

01为什么不能把「扫描结果表」直接当产品？—— 8 层统一产品域模型

1.1 技术事实（L2 IR）与业务治理（Product Domain）的本质分离

在 Lesson 0002 中我们确立了平台底层的 Layer 2 统一 IR（记录组件 PURL、SHA256 与依赖边）。但在真实产品里，企业买的不是“每一次 CLI 吐出来的 JSON 文件”，而是持续可控的资产风险台账。参考 OWASP Dependency-Track v5（Apache-2.0）的实体拆分经验并进一步适配现代化多触点/AI 供应链场景，我们的产品域必须由内向外划分为 8 个职责正交的核心对象：

最常见的致命反模式：Finding 强绑定 Snapshot 一旦把漏洞记录（Finding）直接作为 Snapshot 的子行且不建逻辑定位键，只要研发改了一行注释触发新扫描，昨天的全部 VEX NOT_AFFECTED 豁免和负责人指派就会“原地失忆”，次日 PR 再次全红炸群。
域对象实体 核心主键与定位粒度 可变性 & 生命周期契约 为什么不能与上下层合并？
1. Tenant
租户 / 组织根		 tenant_id (UUIDv7)
私有化单租户固定默认 UUID		 全局隔离边界；挂载商业 SKU 档位、SSO/SCIM 身份源与数据保留策略。 即使第一批只交付单机私有化，表结构里保留 tenant_id 也是零成本实现双模同构的前提。
2. Workspace
事业部 / 业务域		 workspace_id
(tenant_id, slug)		 承载组织权限树（RBAC/ABAC 作用域）与按业务线的合规基线策略。 避免把上万个微服务平铺在一个全局列表里，支撑集团型客户按团队分权分域治理。
3. Project (App)
逻辑应用 / 仓库组		 project_id
绑定 Backstage spec.owner		 承载业务归属团队、重要等级（Tier-0/生产/测试）与统一 MTTR 考核指标。 Monorepo 中一个代码仓常产出多个后端服务、AI 模型与镜像，Project 负责把多形态资产聚回业务主视角。
4. Asset (Target)
具体扫描目标		 asset_id
(project_id, kind, locator)		 区分 SOURCE_MANIFEST、OCI_IMAGE、AI_MODEL_DIR、MCP_CONFIG 与 BINARY。 源码仓根目录与最终上线容器镜像的组件构成、OS 层漏洞及豁免粒度完全不同，必须拆成独立 Target。
5. Snapshot
不可变扫描快照		 snapshot_id
绑定 Commit SHA / Image Digest + cas_hash		 只追加、永不修改（Immutable）：固化某一时刻采集到的 L2 IR 成分图与工具指纹。 保留时间点真实历史，用于 PR 增量 Diff、历史版本回溯与 EU CRA 合规审计还原。
6. LogicalFinding
活体风险与漏洞台账		 finding_id
稳定指纹（asset_id + branch + purl_key + rule_or_vuln_id + symbol）		 跨 Snapshot 持续演化状态机（OPEN / FIXED / REOPENED / SUPPRESSED / VEX_NOT_AFFECTED）。 实现“新扫描仅刷新 last_seen_snapshot，0-day 夜间爆发不重跑 CI 也可由后台直接生成或更新 Finding”。
7. Policy & Waiver
策略决策与人工豁免		 waiver_id + vex_statement_id
绑定 finding_id 或全局策略作用域		 带有效期（expires_at）、审批人、Justification（遵循 OpenVEX）与自动到期重激活。 人工审计心血属于独立审计资产，绝不可随某次构建日志过期清理而销毁。
8. RemediationTask
聚合修复与触达工单		 task_id
按「同一 Project + 同一修复升级动作」聚类		 把多条同源 CVE（如升级 log4j-core 一次性解决 6 个漏洞）聚合成 1 个 PR / 1 条 Agent 修复指令。 彻底把“漏洞数据库记录”与“打扰研发的工作流动作”解耦，防止 PR 风暴与工单轰炸。

1.2 发版封板模型：如何解决“活体台账”与“历史不可变审计”的矛盾？

EU CRA 与金融/车企合规审计常要求回答：“半年前发布的 v3.2.0 版本，当时为什么允许带某高危组件上线？”如果只保留活体 LogicalFinding，半年后该漏洞可能已被修复或豁免已过期，历史现场随之丢失。工程解法是在 Snapshot 与 Policy/Waiver 之上增加一个轻量 ReleaseBundle（发版封板视图）：仅在发版打 Tag 时，将对应 snapshot_id、生成好的 CycloneDX SBOM/NOTICE 对象指针、以及当时生效的 Waiver/VEX 审批列表做一次不可变签名冻结，日常分支扫描与发版审计各行其道。

02五类角色旅程与 4 条端到端产品闭环（拒绝“漏洞堆积表”）

传统第一代 SCA 只服务安全工程师看报表，最终沦为“安全部自娱自乐的万条红字表格”。参考 OWASP SAMM 的安全左移与治理度量思路，现代全场景 SCA 必须让五类关键干系人各自在自己顺手的界面里走通闭环，同时共享同一份底层真值：

产品干系人角色 核心痛点与工作面 端到端闭环动作（Input → Verdict → Action） 产品域核心状态流转
1. 研发 / AI Agent
（写码与提 PR）		 痛恨万条存量告警与打断节奏；工作面在 CLI / MCP / Hook 与 Git PR。 Agent 装包前调 MCP 拦截幻觉/投毒包；PR 仅对净新增且可达（Reachable）的组件触发单条聚合修复建议。 Snapshot(PR Diff) → RemediationTask(PR_BOT / MCP_JSON)
2. AppSec 工程师
（研判与规则运营）		 每天被无效告警和跨团队扯皮淹没；需要快速证明“为什么不用修”。 核验静动态调用链证据，一键签发带过期时间的 VEX NOT_AFFECTED；0-day 突发时 10 秒定损并批量派发聚合工单。 LogicalFinding → Waiver / OpenVEX → 同步刷新工单
3. DevOps / SRE
（流水线与集群）		 担心扫描拖慢 CI、源码出内网或 K8s 准入单点宕机。 配置快/慢双路径门槛；部署 Hybrid Runner 出站同步；集群网关仅做毫秒级 SLSA VSA/CEL 验签准入。 Asset(CI/Registry) → Snapshot → ReleaseBundle / VSA
4. 法务 / OSPO
（开源合规审查）		 手工核对 NOTICE、担心静态链接强传染及 AI 训练数据版权。 基于 Declared/Observed 冲突队列做一次 Curation 覆写（全项目继承），发版自动生成可审计合规归档包。 Snapshot + License Curation → ReleaseBundle
5. CISO / 管理层
（度量与监管汇报）		 需要向董事会证明降噪成效、MTTR 下降与满足法规死线。 只看经过可达性与 VEX 过滤后的真实风险水位、各团队 SLA 达标率以及 EU CRA / SSDF 导出报告。 基于 Workspace / Project 聚合只读 OLAP 趋势指标

03「一核三阶」Feature Entitlement 与双模一致体验契约

3.1 切忌在业务代码里写 if isOnPrem || tier == "pro"

你的产品第一天就要兼容「公有云 SaaS（按组织动态计费升级）」与「Air-Gapped 私有化（按离线 License 文件解锁）」，同时还要承载 Lesson 0022 定下的 Tier 1 Starter / Tier 2 Pro / Tier 3 Sovereign 三阶 SKU。对于 1 人 + AI Agent 团队，最灾难的做法是维护两套分支代码或在几百个 handler 里硬编码 if tenant.DeploymentMode == "onprem"。

正确解法是采用 CNCF OpenFeature（Apache-2.0）建立一层薄而稳定的 Capability & Entitlement Gateway：业务与 API 层永远只询问语义化能力键（例如 reachability.static.enabled、ai_bom.scanner.enabled、deploy.hybrid_runner.max_seats），而具体数值从哪里算出来，由启动时注入的 Provider 决定：

  • SaaS 模式 Provider：读取中心化 Entitlement 表（带短 TTL 本地内存缓存），支持租户在线增购、7 天试用解锁或针对特定大客户的灰度开关。
  • 私有化 / 离线模式 Provider：启动时使用内置公钥校验离线签名 License 文件（我们将在 Lesson 0026 详解 Ed25519 签发机制），直接把离线证书里的权限矩阵映射成一模一样的 OpenFeature Evaluation Context。
双模一致体验（Parity by Design）铁律 私有化客户同样有权限升级模块、也会碰到“未购买 Pro 模块时点击可达性 Tab”的场景。通过统一 Entitlement 接口返回明确的 FEATURE_NOT_ENTITLED 状态码，前后端逻辑 100% 复用，1 个人也能稳稳驾驭双线交付。
