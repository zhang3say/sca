容器镜像、OS 发行版与制品分层采集原理

源码没有锁文件时是「盲区」，而交付上线前的容器镜像与编译产物才是运行态唯一真相。但千万别用 docker run 进容器敲命令——本课直击用户态 OCI 分层与 Whiteout 合成、Distroless 与三代 RPM 数据库解析、以及 Java Fat-JAR / Go / Rust 静态二进制的内嵌依赖采集底层。

本课收获：掌握零挂载用户态镜像 Squash 算法、4 大 OS 包 DB（含源码包映射）与 3 类二进制内嵌段提取及防 Zip Bomb 边界 先修底座：Lesson 0002 · Lesson 0004
承上启下（对齐你的 Mission）

在 Lesson 0004 我们敲定了以 Syft + OSV-SCALIBR 为核心的 Go 泳道 A，并把交付产物定义为 Tier 4（置信度 0.96–0.98） 权威源。今天揭开 Tier 4 的内部黑盒：为什么纯静态用户态扫描必须自己还原 overlayfs 语义？为什么扫出 libssl3 还不够，必须挖出 Source: openssl？以及如何拆解被剥离符号表的 Go/Rust 二进制与嵌套 JAR。

01OCI 镜像分层解剖与 Whiteout 虚拟文件系统合成

初代镜像扫描器常犯两个致命错误：要么在 Worker 里调用 docker run / exec 进容器执行 dpkg -l 或 rpm -qa；要么把每个层 Tarball 独立解压到宿主机或逐层扫描再拼并集。

前者的死穴在于：① 不可信镜像 Entrypoint 存在容器逃逸/RCE 风险；② Distroless / scratch 镜像压根没有 /bin/sh 和包管理器可执行文件；③ 跨架构镜像（如在 x86 扫描器扫 ARM64 镜像）无法直接执行。而逐层独立扫描不合成目录树，则会直接炸出“已删除文件仍在告警”的幽灵误报。

为什么禁宿主机 mount？ 在 Kubernetes 多租户扫描 Pod 里调用内核 mount -t overlay 需要特权模式（CAP_SYS_ADMIN），直接把安全扫描器变成宿主机提权跳板，政企客户安全基线一票否决。现代底座一律采用纯用户态内存 VFS 合成。

工业级底座（如 Anchore Stereoscope 与 Google go-containerregistry，均为 Apache-2.0）严格遵循 OCI Image Spec，在用户态流式解析 manifest.json → config (diff_ids) → layer.tar.gz，并按层号从底向上回放两类删除标记（Whiteout）：

  • 单文件删除标记（.wh.<filename>）：同一层某目录下存在 .wh.curl，等价于声明“把所有更低层该路径下的 curl 文件或目录从最终视图中抹除”。
  • 不透明目录标记（.wh..wh..opq，Opaque Whiteout）：当上层构建命令清空并重建某目录时，该目录内会出现 .wh..wh..opq，意味着屏蔽全部更低层该目录下的所有兄弟文件与子目录，仅保留当前层及更高层新增内容。

02Linux 发行版包数据库与 Distroless 无包管理器镜像解析

合成出终态 VFS 后，Layer 1 采集器无需执行任何二进制程序，直接以只读方式读取各 Linux 发行版的静态包数据库文件与系统指纹（/etc/os-release 或 /usr/lib/os-release）。

这里藏着商业产品最容易踩穿的两大工程暗坑：① 路径与数据库引擎代际分裂（尤其是 Distroless 碎片化目录与 RHEL 9 SQLite 迁移）；② 丢失「二进制包 → 源码包（Source / Origin）」血缘字段。

为何必须抓 Source / Origin？ 在 Debian/Ubuntu/Alpine 中，一个源码包（如 openssl）编译时会拆出十几个二进制子包（libssl3、openssl-dev），而 Debian Security Tracker 和 OSV 公告常常按源码包名发布！只记 libssl3 不写 upstream=openssl，Layer 3 匹配必定大批漏报。
发行版家族 静态数据库路径（含极简/现代路径） 存储格式与 Go 底座 关键提取字段与源码包映射 高危工程暗坑
Debian / Ubuntu / Distroless /var/lib/dpkg/status
/var/lib/dpkg/status.d/*		 RFC 822 文本段（Status: install ok installed）；纯 Go 直接流式读取 Package、Version（带 epoch/revision）、Architecture、Source（填入 PURL upstream） Google Distroless 无 status 总表，只留每包独立文件于 status.d/；同时必须过滤非 installed 状态残留。
Alpine Linux /lib/apk/db/installed 单字母行前缀 KV 文本块；纯 Go 直接解析 P: 包名、V: 版本、A: 架构、o: origin 父源码包 忽略 o: 字段会导致子包（如 musl-utils 对应 musl）丢失源码包索引。
RHEL / CentOS / Fedora / UBI /var/lib/rpm/*
/usr/lib/sysimage/rpm/*
/usr/share/rpm/*		 三代格式：BDB Packages / NDB Packages.db / SQLite rpmdb.sqlite；底座 go-rpmdb (MIT, 零 CGO) Name、Epoch:Version-Release、Arch、SourceRPM、Vendor / ModularityLabel RHEL 9 / Fedora 移除了传统 BerkeleyDB，迁移至 /usr/lib/sysimage/rpm/rpmdb.sqlite；如果 Go Worker 依赖 librpm CGO 绑定将直接丧失跨平台编译与镜像兼容能力。
OS 身份识别 /etc/os-release
/usr/lib/os-release		 Shell KV 文本；优先读 /etc/os-release，缺失回退 /usr/lib/os-release ID + VERSION_ID → 组装 PURL ?distro=debian-12 / rhel-9.4 忽略 distro 限定符会让 Layer 3 把 Debian 的 3.0.11-1~deb12u2 误当上游原生版本比对，引爆 Backport 误报灾难。

03编译交付制品深层提取：Java Fat-JAR、Go 与 Rust 二进制

如果容器里跑的是一个把业务塞进 FROM scratch 的静态编译 Go/Rust 可执行文件，或者一个 100MB 的 Spring Boot Fat-JAR，OS 包数据库是空的——Layer 1 必须具备深入归档嵌套结构与二进制链接器专用段的解构能力。

1. Java JAR / Fat-JAR / Uber-JAR

归档递归流式解压 vs Shade 打平盲区
  • 标准 & Spring Boot 嵌套 JAR：
    识别 BOOT-INF/lib/*.jar 或 WEB-INF/lib/*.jar，递归提取内嵌 META-INF/maven/<g>/<a>/pom.properties（groupId、artifactId、version）与 MANIFEST.MF，记录 virtual_path（如 app.jar!/BOOT-INF/lib/spring-web-6.1.4.jar）。
  • Maven Shade / Shadow Uber-JAR 盲区：
    Shade 插件把所有依赖 .class 打平合进同一个根目录，甚至做 Relocation 类路径重定位（com.google → shaded.com.google），且默认剥离或覆写 pom.properties 并生成抹除依赖的 dependency-reduced-pom.xml。
  • 架构破局三连击：
    ① 允许流式提取但设定防 Zip Bomb 安全阈值（最大递归深度 3 层 + 累计解压字节限额 + 校验 ZipSlip ../）；② 对无 pom.properties 的打平 JAR 用包名/常量池指纹低置信度标记提示；③ 最佳实践是在 CI 阶段 Shade 执行前用 cyclonedx-maven-plugin / ORT 采集 Tier 3 BOM 按制品 SHA-256 关联对齐。

2. Go 静态编译二进制（ELF / PE / Mach-O）

.go.buildinfo 抗剥离段与标准库节点
  • 剥不掉的 .go.buildinfo 元数据段：
    Go 1.18+ 编译器把主模块、全部生效依赖与编译器版本写入专用节区。即便上线前执行 go build -ldflags="-s -w" 和 strip 删光了 DWARF 调试符号，通过标准库 debug/buildinfo 依然完整可读！
  • 高频漏报与误报双坑：
    ① 漏扫 Go 标准库：BuildInfo.GoVersion（如 go1.22.1）必须主动生成一个 pkg:golang/stdlib@1.22.1 组件节点，否则 net/http、crypto/tls 漏洞全部漏报；② 忽略 Replace：若某模块被 replace 替换为新版本或修复分支，必须优先入库生效的 dep.Replace 版本。
  • 底座支撑：
    Syft 与 OSV-SCALIBR 均内置基于 debug/buildinfo 的二进制提取器，可在 scratch 镜像中 0 源码 100% 还原 Go 精确依赖清单（含 VCS Commit 与构建标签）。

3. Rust 编译二进制（ELF / PE / Mach-O）

默认失明盲区 vs cargo-auditable .dep-v0
  • 默认构建的黑盒痛点：
    不同于 Go，默认 cargo build --release 编译产物只保留机器码，一旦执行 strip 或丢弃源码仓里的 Cargo.lock，只看二进制文件几乎无法准确还原所用 Crate 的精确版本。
  • cargo-auditable（MIT/Apache-2.0）破局机制：
    在 CI 中用 cargo auditable build --release 编译，工具会将经过 zlib 压缩的确定性 JSON 依赖树（不含本地绝对路径与时间戳，保持可复现构建）直接嵌入二进制专用链接器段 .dep-v0。
  • 底座对齐与生态推进：
    Syft（≥ v1.15.0）与 OSV-SCALIBR 均原生支持自动识别并解压 .dep-v0 段还原完整 pkg:cargo/* 树。商业平台应在接入指南中把 cargo-auditable 作为 Rust 制品扫描的“黄金前置规范”，未嵌入时再降级提示使用源码 Cargo.lock。
Layer 1 归档与二进制解析的防 DoS 安全红线

容器与制品解压是极易遭遇恶意载荷（Zip Bomb / Tar Bomb）攻击的入口！无论是内存合成层 Tarball 还是递归解包 Fat-JAR/Wheel/TAR，底层代码必须强制注入四重硬限制：① 递归嵌套最大深度（如 ≤ 3–5 层）；② 单文件与单归档累计解压字节上限（如使用 io.LimitReader，严禁无界 io.ReadAll）；③ 路径规范化拒绝 ../ ZipSlip 穿越与无限循环符号链接；④ 单个文件扫描超时熔断。

一手必读原典（Primary Source）

编写容器镜像合成器、OS DB 提取器与二进制制品插件时，建议对照以下一手规范与商用合规代码库：
