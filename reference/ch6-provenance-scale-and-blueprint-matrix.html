01SLSA v1.2 双轨规范、in-toto DSSE PAE 与 VSA 核心速查（Lesson 0020）

规范 / 协议层 权威标识 / 核心字段 关键技术机制与防线意义 高危踩坑与强校验铁律
SLSA v1.2 Build Track
（L1 – L3 · 构建完整性）		 https://slsa.dev/provenance/v1
SLSA_BUILD_LEVEL_1..3		 L1 产出机器可读 Provenance；L2 托管构建平台 + 密码学签名（防构建后篡改）；L3 加固临时化隔离 Runner（防构建中篡改）。 只验 Build Track 无法阻挡拥有写权限的内鬼或被盗账号直接向 main 推入恶意代码触发正规构建。
SLSA v1.2 Source Track
（2025-11-24 正式定稿 · L1–L4）		 SLSA_SOURCE_LEVEL_1..4
Source Provenance / Source VSA		 L1 VCS 不可变 SHA + Diff；L2 防强推历史保留 + 实时 Source 证明；L3 保护分支持续技术控制；L4 严格 Two-Party Review。 连续性铁律 Onboarding & Continuity：仅从接入后生效（不做历史追溯）；临时关闭分支保护即断链降级。
in-toto v1 + DSSE PAE
（不可伪造声明信封）		 _type: https://in-toto.io/Statement/v1
payloadType: application/vnd.in-toto+json		 subject[].digest 绑定不可变 SHA-256；签名基于 PAE(type, payload) = "DSSEv1" + SP + LEN(type) + SP + type + SP + LEN(payload) + SP + payload。 禁止对原始 JSON 做脆弱文本规范化签名；PAE 绑定精确字节长度与 payloadType，彻底杜绝 Type Confusion。
SLSA VSA v1
（消费端预验签摘要）		 https://slsa.dev/verification_summary/v1
verifier.id / verifiedLevels		 中心策略引擎验签全量依赖与 Build/Source 连续性后签发极简结论（verificationResult: PASSED），供集群/客户毫秒级准入。 避免每个 K8s 准入节点重复拉取并递归重算上百层原始 Provenance 日志，同时隐藏内部构建敏感细节。

03海量资产 CAS 去重、三层存储与 10 秒 0-day 检索矩阵（Lesson 0021）

架构组件 / 机制 权威架构对齐 / 关键接口 核心数据结构与执行流水线 规模化收益与避坑底线
开源底座收敛与 CAS 去重 GUAC v0.6.0+ (PG ent) · Dependency-Track v5 (PG 状态协调) 入库前对规范化依赖子图计算 dep_tree_hash = SHA256(...)；未改锁文件的 CI 构建仅写轻量 snapshot_ref 指针。 压缩 90%–96% 重复依赖边写入与索引体积；严禁每日把全量原始 CycloneDX JSON 塞进主库热表。
Hot / Warm / Cold 三层分流 Hot: PostgreSQL 分区
Warm: ClickHouse (Apache-2.0)
Cold: S3 Zstd Parquet		 Hot 只留默认分支最新与线上运行中 Digest；Warm 存 30–90 天 MTTR/漏洞趋势 OLAP；Cold 归档 1–7 年原始 SBOM/Bundle WORM。 彻底把重度 GROUP BY 运营大盘报表从主库剥离，避免运营查询拖垮门禁与实时检索。
10 秒 0-day 三段检索 RoaringBitmap/roaring/v2 + PG 14+ CYCLE 内存执行 roaring.And(idxPurl, idxProd, idxReach)（<2ms）收敛命中集；再对命中子图运行 WITH RECURSIVE ... CYCLE child_id SET is_cycle USING path。 避免对全网万级项目直接递归与正则扫 JSONB；PG 14+ 标准 CYCLE 彻底杜绝 npm/Maven 循环依赖死循环。
Backstage 团队归属路由 Backstage catalog-info.yaml (Apache-2.0) 以强制字段 spec.owner（指向 group:default/team）+ CODEOWNERS 聚合上百应用为十几张团队工单。 严禁按个人派单 人员离职或调岗会导致 Git 初次提交邮箱失效，催生数千条无主孤儿漏洞。

04图数据库许可排雷与 CEL vs OPA 双策略热更新矩阵（Lesson 0021）

底座 / 策略引擎 精确许可协议 执行模型与延迟边界 商业闭源选型与安全发布铁律
PostgreSQL + Apache AGE vs Neo4j / ArangoDB / Memgraph PG / AGE (Apache-2.0)
vs Neo4j (GPL-3.0) / ArangoDB & Memgraph (BSL)		 PG 原生递归 + CTE + 可选 AGE openCypher 覆盖绝大部分供应链深度遍历（通常 ≤ 32 跳），无需独立维护重型图集群。 商业红线 严禁将 GPL-3.0（Neo4j 社区版）混编进闭源产品，或将受商业托管限制的 BSL 数据库转售为 SaaS。
google/cel-go
（K8s 1.30 VAP 原生内核）		 Apache-2.0 非图灵完备（无无界循环，数学保证有界终止），编译期类型校验，进程内微秒级求值（无 Webhook 序列化跳数）。 专守热路径 0-day 急停与 K8s 原生准入（ValidatingAdmissionPolicy GA 于 Kubernetes 1.30）。
open-policy-agent/opa
（Rego 通用策略引擎）		 Apache-2.0 图灵完备 Rego，擅长跨系统、多文件上下文与递归合规推理；作为外部 Webhook 运行时存在网络序列化延迟与可用性风险。 与 CEL 形成双引擎分工，承接复杂合规审批（许可证 + VEX + 豁免流）；热路径切勿全流量走重型外部 Webhook。
0-day 策略热更新与灰度铁律 Go atomic.Pointer
Shadow Dry-Run → Enforce		 策略编译器预校验后通过 atomic.Pointer 原子切换热加载，全节点亚秒生效无需重启 Pod。 严禁盲切硬阻断 必须先走 Shadow Dry-Run 预览爆炸半径再切 Enforce，且必留 VEX 自动豁免与带审计紧急热修旁路。
